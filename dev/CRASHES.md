# Crash logs

The loader (`src/loader/CrashLog.cpp`) installs a crash logger before anything else runs. On a crash anywhere in the game's process, it writes `crash-<date>-<time>.log` beside the other logs, in `Documents\BioWare\Dragon Age\daolib\` (under OneDrive on this machine), and puts a line pointing to it at the end of `loader.log`. Built 2026-09-30, on the shape of Skyrim's CrashLoggerSSE.

## What a log holds

| Section | What |
|---|---|
| Header | The exe's link stamp, whether it is the build DAOLib knows, the time |
| Unhandled exception | The code by name, the address and what it is, for an access violation the address read or written, and the first bytes of code at the fault. For an access violation also what the address space held at that address and just before its page, asked in the filter: free, reserved or committed, and whose mapping. A read a little past the end of memory that is there shows as a page before that is committed and a page there that is not (DAOLib #105). |
| ADDRESS SPACE AT THE CRASH | How much of the process's address space was in use and its largest free block, measured in the filter before anything is allocated. When the largest free block is under 16 MiB it says the space was all but full and that a failed allocation is the likely cause ("Out of address space", below). |
| SYSTEM | Windows, physical memory, and the process's address space. DAO is 32-bit, so address space runs out long before memory does. |
| PROBABLE CALL STACK | dbghelp's walk of the crashing thread. Exact through our DLLs and Windows, with file and line for ours. It can stop early in the game's own code, which has no frame data. |
| RETURN ADDRESSES ON THE STACK | Every value in the stack's first 64 KiB that is a return address into any module (`dao/core/CallSite.h`), the first 128 of them (64 until 2026-10-02, which stopped one crash's list a frame short of the caller that mattered). This keeps going where the walk stops: the game's callers, innermost first. A few may be stale values from earlier calls. |
| REGISTERS, STACK | Each value annotated: code by its module and function, an engine object by its RTTI class (`(CCCreature*)`), a string (`char*` or `wchar_t*`), or a small number |
| GFF4 FILES ON THE STACK | A stack value in the first 64 KiB that points at a GFF4 file's bytes: a file the game is reading. Its length is the word after it (the game passes a file's bytes so) or else as far as the memory goes; a copy is parsed (`dao/core/Gff4.h`) and the line gives the file's type, its root's template and the root's strings by label (`dev/gff4_fields.csv`). For a model that is `6000`, `MMHName`, the model's name. |
| ENGINE STRINGS IN THE STACK'S FRAMES | The engine's `std::wstring`s lying in the stack's first 64 KiB (`dao/core/StackText.h`): a function's own strings, the name of the file or object it is loading among them. Each text once, innermost first; some are left over from earlier calls. |
| MODULES, DAOLIB PLUGINS | Everything loaded, with its range; our plugins |
| LAST LINES OF ... | The last twelve lines of each log this game wrote in this run: `<name>.log` for the game that has the plain names, `<name>.<process id>.log` for one started beside it, and only a file written since the game started. The folder is shared with the games running beside it and keeps what earlier ones left, and a report used to quote them all (DAOLib #57: a crash log of 1,390 lines, most of them old sessions; with the rule, seen 2026-10-12 with the probe's deliberate crash, 359 lines quoting three logs of the folder's 24). No report (`crash-`, `hang-`, `exit-`) and no `.previous.log` is quoted. |

Names come from three places:
- **Our DLLs:** their PDBs, which `tools\deploy.ps1` copies beside them.
- **Windows DLLs:** their exports.
- **The game:** `bin_ship\daolib\functions.tsv`, Ghidra's function list, which deploy also copies (`dev/PROBE.md` says how to export it). With it, `0x0073D054` reads as `FUN_0073d000+0x54` or `GameModeGUI::vfunction7+0x1c`. Without it, the game's addresses stay bare. The names are of the GOG build's addresses. In the EA app's build (`dev/BUILDS.md`) an address in the game is given as that build's own, then as GOG's, by which the name is found: `DAOrigins.exe 0x004c1770 (GOG 0x005d6740) CClientExoApp::SetPaused+0x0`, or `(not in the GOG build)` for code EA's build alone has. Written 2026-10-01 and not yet seen: no crash has been made in the EA game.

## Hang logs

A stall that ends leaves no crash log, so the loader also keeps a watchdog (DAOLib issue #4, for a 32-second stall in a turn-based fight, 2026-10-03). It counts frames with `dao::OnFrame` and checks once a second from a thread of its own. When no frame has come for 5 seconds (`DAOLIB_HANG_SECONDS` in the game's environment; 0 turns it off), it writes `hang-<date>-<time>.log` beside the crash logs:

- **A sample.** The frame thread is suspended for as long as it takes to copy its registers and its stack's first 64 KiB, and nothing is allocated meanwhile, since the thread may hold the heap's lock. The log is written from the copy while the game runs on: the registers, the return addresses, the stack, the GFF4 files and engine strings on the stack, as a crash log has them. There is no call stack walk, since dbghelp would walk the live thread. Memory the stack points at, a file's bytes or a string's heap text, is read after the thread is let go, so it may have changed.
- **What the game was doing.** Each sample says the game's mode, and whether its window was in front, not in front, or what Windows calls not responding.
- **While it lasts.** Another sample every 5 seconds, twelve at most. A sample whose return addresses match the one before is a loop or a wait; one that differs is the thread making slow progress.
- **The first sample** also has the system, the modules, the plugins and the last lines of every log, what led into the stall.
- **The end.** When frames come back, the last line says after how long: from the last frame to the first one after it, as the frame callback saw them, not to when the watchdog, perhaps still writing a sample, noticed (fixed 2026-10-04, DAOLib #20: a stall of 5.6 s had been written as 15.5). `loader.log` says when a hang log was begun and when frames came back.
- **Other threads.** The first sample of a stall also lists every other thread of the process, sampled just after the frame thread, each with its instruction and first callers (DAOLib #30): a frame thread waiting for a lock shows the lock's holder there. Asked for after 2026-10-05 17:43:38, a 5.6 s stall with the frame thread waiting for the process heap's lock in a debug free, its holder unseen.
- **Rooms owed.** Each sample's state line says how many of the area's rooms were wanted and not loaded, and how many were loading, at the last frame, counted by the loader's frame callback (DAOLib #20's follow-up, 2026-10-04). Seen in two stalls, 2026-10-05: both read "1 room(s) wanted and not loaded, 0 loading" with no streaming under way, so one room owed is the Dead Trenches' steady state, and the count to read is the rooms loading. An outdoor area's terrain cells are not counted (DAOLib #29): two stalls on 2026-10-05 at 16:11 and 16:12 read "179 loading", the same in both, which were the cells.
- **Reading what the stack points at.** Both logs follow every stack word that looks like a pointer, and some point into a thread's stack guard page. Reading one raises `STATUS_GUARD_PAGE_VIOLATION`, which `dao::TryCopy` does not catch (`tests/test_saferead.cpp`). A crash log on 2026-10-03 ended mid-way that way (issue #9). Every such read now asks `VirtualQuery` first, region by region, and goes ahead only where the pages are committed, readable and not guards (`dao/core/Pages.h`).
- **When not.** Before the game has a mode, while loading and at the main menu's start-up, where frames may stop by design. Not with the window minimised, or gone, as the game closes.
- **Seen in play**, 2026-10-03, in the turn-based playthrough (GOG): from 01:28 on, through four launches and three quits, five loads (two from inside a fight), two area transitions, a skipped cutscene, the Store screen and some six fights of up to 19 rounds, it wrote no hang log: none at launch, at exit, in a load or in a menu, and no stall came. The game was in front throughout, so whether frames stop with it behind another window is not yet seen. A real stall's log is not yet seen either.
- **The first real stall**, 2026-10-04 13:52:44 (GOG, the turn-based mod and Eluvian loaded): no frame for 9.9 s in explore mode, the window in front, Windows calling it not responding; then frames came back, and the log said so after one sample. The frame thread was in the game's graphics update (`Eclipse::IGraphicsInternal` slot 21, `0x0052A090`), yielding in a loop (`0x00A1ECE0`, `SwitchToThread`): waiting on another thread, most likely the renderer's. The plugins' frame callbacks are only above it on the stack. It fell inside a load: a save into the caverns above Haven (a big area, a dozen creatures spawned) about 40 s after launch, with no tool call in flight (the Eluvian and turn-based sessions, corrected the same day). So it is a load's first frames with the mode already reading Explore, past the watchdog's "while loading" by mode: harmless, one log and then frames back. If more come so, the watchdog could wait out the first seconds after an area's load; not changed on one case.
- **The second**, 2026-10-04 16:11:42, in a fight (the random encounter `ran500ar_hw_army_redcliffe`, the turn-based mod at fight speed 3): no frame for 5.6 s by the mod's frame callback (the log said 15.5 s, the end measured when the watchdog noticed; DAOLib #20). The frame thread was drawing, in the game's material and texture setup (`Graphics::MaterialObjectInstance` slot 3, `MaterialPass` slot 4, `D3DTextureCubeMap`, with `SpeedTreeForest` on the stack). It began 0.6 s after the mod's camera jumped onto an enemy, so rooms streaming in after the jump is the likeliest reading (the Eluvian session's); the processor was at 75 to 97 % with three test runs going. Then Windows took the window from the front for 0.7 s, as it does for one that has not pumped messages for five seconds.
- **The third and fourth**, 2026-10-05, in a turn-based fight in the Dead Trenches (try-20-23's loader, the turn-based mod's master build, the Eluvian server). At 00:48:03, 6.0 s with the window in front, one sample: the frame thread in the turn-based mod's own frame callback (`Bridge::Observe`, `Status`, `Energy`, `GetCreatureProperty` through `dao::script::Invoke`), so its per-frame work, told to its session. At 00:49:55, the window having lost the front at 00:49:49: twelve samples, each the frame thread sleeping in the graphics driver (`D3DDriver::D3DGraphicsDriver` slot 89, `Sleep`, under `Renderer` slot 9 and the graphics update), as the game waits while it is not in front; frames came back 121.3 s after the last one, when the window had the front again (00:51:50), which the Eluvian server's own time since a frame (116.7 s five seconds before) agrees with (DAOLib #20). Both recovered; the fight went on.
- **The fifth and sixth**, 2026-10-05 16:11:04 (6.0 s) and 16:12:32 (5.5 s), in a fight, the window in front, both recovered. The first's one sample had the frame thread in the Eluvian server's frame callback, copying a large `nlohmann::json` under the debug runtime's heap (`RtlValidateHeap` inside `RtlAllocateHeap`), told to its session; the second's in the graphics update's wait (`0x00A1ECE0` under `IGraphicsInternal` slot 21), as the first stall's was. Their room counts read the terrain's cells (DAOLib #29).
- **A character with hundreds of saves.** Every autosave and quicksave makes the game rebuild its list of the character's saves first, opening a file in each save's folder, so the stall grows with the number of saves (DAOLib #36). 2026-10-05 21:20:27, 5.1 s: the scripts' `AUTOSAVE` at a conversation's start, into `SaveLoadProxy::HandleMessage_SaveGameMessage`'s autosave branch (its call to `0x006D15D0`, which sets an attribute of the data tree, `0x006CBF10`, whose observers rebuild the list), caught opening `Slot_98`'s `screen.dds` through `SaveLoadProxy::ScreenshotPath`; the character had about 500 manual saves, the most the engine allows (`dao::saves::MostSlot`), made by a test driver. Keep a test character's saves few. First read as OneDrive holding a file (the saves are under a synced `Documents` here), which may slow each open but is not the cause. A machine saturated by build or mutant workers makes every stall longer, so a stall during one is weak evidence of anything.

## How it stays installed

It is an unhandled-exception filter, and the game's C runtime installs one of its own at start-up. So the logger also detours `SetUnhandledExceptionFilter`. A filter the game sets afterwards is remembered and called after ours, so the game's own handling still happens, and Windows Error Reporting still records the crash. The log is written on a new thread, because the crashing thread may be out of stack. The crashing thread waits up to a minute for it.

## Out of address space

The game is 32-bit, and Steam's and EA's executables are not large-address-aware: 2 GiB of address space, where GOG's has 4. A long session there ends with the space full and an allocation failing, and the crash that follows can be in any code: the play tester's, 2026-10-10 in Steam's game, was an access violation in `D3DDriver::D3DTextureVolume::vfunction22+0x27` (GOG `0x00874AB7`) with the process at 1,999 of 2,048 MiB and a largest free block of 3 MiB. The log of it was an empty file (DAOLib #56): the report allocates (the module list, the function names, dbghelp's symbols, every line it formats), and an allocation failing on the writer's thread ended the process with nothing written.

So the loader reserves 16 MiB of address space when the crash logger is installed, before any game code runs: reserved and not committed, so it costs no memory, and at the top of the space, away from where the game's allocations grow. The filter measures the address space (a walk of `VirtualQuery`, which allocates nothing), releases the reserve, and only then starts the writer's thread. The measurement is the log's ADDRESS SPACE AT THE CRASH section, and when the space was all but full `loader.log` says so in one line as well. An allocation that fails even so ends the log with "The log ends here: writing it failed", not the process.

## Testing it

With `DAOLIB_PROBE_CRASH_TEST=1` in the game's environment, the probe crashes on purpose on the game's thread, in the first `SetPaused` at start-up. Start the game with the variable set only for that run:

```powershell
$env:DAOLIB_PROBE_CRASH_TEST = '1'; Start-Process "...\bin_ship\DAOrigins.exe" -WorkingDirectory "...\bin_ship"; Remove-Item Env:DAOLIB_PROBE_CRASH_TEST
```

The log from that test (2026-09-30) named `CrashIfTesting` at `Probe.cpp:63`, the hook at `Probe.cpp:87`, the engine's `FUN_005DD310` below it, and the chain down to `Eclipse::UpdateTask` on a `Multithreading::Thread`.

With `DAOLIB_PROBE_CRASH_TEST=2` the probe fills the address space first: it reserves every free block of 64 KiB or more, the largest first, so no `VirtualAlloc` can succeed, and then crashes the same way. The log must be whole all the same, written in the 16 MiB the loader kept back, with "All but full" in its ADDRESS SPACE AT THE CRASH section.

**Seen in play 2026-10-10**, by the play tester with the release build that became 0.1.0 (`version.dll` SHA-256 `46B57896...1A2CF`), the first time a release build ran in the game:

- **`1`, GOG's game:** a log of 1,063 lines. "1643 of 4096 MiB in use, largest free block 2030.3 MiB", and no "All but full". The call stack's first frame is `probe.dll+7D26 SetPaused+0x136 (Probe.cpp:142)`, then the engine's `FUN_005dd310+0x3f`: a release build inlines `CrashIfTesting` into the hook, so the frame has the hook's name, with the file and line of the write. The release PDBs name our frames.
- **`2`, GOG's game:** a whole log, 1,066 lines through its LAST LINES sections. "4089 of 4096 MiB in use, largest free block 0.1 MiB", "All but full", the same call stack, and `loader.log`'s line.
- **`2`, Steam's game**, the build the fix is for: a whole log, 1,066 lines. "2042 of 2048 MiB in use, largest free block 0.1 MiB", "All but full", the probe's frame named the same way.

So 16 MiB is enough for the report with the loader's PDB and two plugins' (8 MiB each) to read. It was not tried with more plugins than that, nor with `functions.tsv` in Steam's folder.

## The crashes it has explained

- **2026-09-30, the probe's queue hook.** `strnlen` in `dao::DecoratedTypeName`, reading `0x84C6CF93`. Its check that a pointer lies inside the exe's image computed `end - address` without first checking `address < end`. An address above the image wrapped the subtraction around and passed. A command object's garbage word took that path. The check is now `dao::core::Contains` (`tests/test_range.cpp`), and the crash before it, in `memcpy`, was almost certainly the same bug.
- **2026-09-30, a creature's properties.** An access violation reading `0x14` at `0x006436EB`, in the engine's property getter, called from `dao::CCCreature::Property` in the example plugin's frame callback; the log named `ESI` a `CCCreatureStats*`. The getter was given the creature's stats, but `GetCreatureProperty` gives it the stats' property list, 0x190 bytes in (`lea ecx, [eax + 0x190]` at `0x0066D002`). On the stats themselves it read another vector, whose entry for strength was `0x104FF`, and called through it. The register naming the class was the clue that the object was right and the offset wrong. `Property` now adds 0x190; the setters take the stats and add it themselves (`0x0071B239`).
- **2026-10-02, an effect's model as a turn-based fight began** (DAOLib issue #3). An access violation at `0x004C24D7` in `std::wstring(const wchar_t *)` (`0x004C2480`). The engine was parsing a model hierarchy (`GFF V4.0PC  MMH V0.1`, 7566 bytes, on the stack) and read `MMHName` (6000) of an emitter group's node (`0x00591070`) from a place that held the float -10.0, as a string's offset. The return addresses lead from the model blueprint loader (`GraphicsStructuresManager` slot 40) up through the graphics layer to `VfxManager::Place`+0x39: the effect's model was loaded as the effect was placed, synchronously on the game's main thread. The turn-based mod's log has no preview in that run, so the `Place` was the game's own. A replay of the same steps passed, and the file's header was intact, so the bytes or the parse's position were different that once: memory changed under the parse is a guess, not read. The log could not say which model: the return-address list stopped at its cap of 64 at `Place`, and the buffer and the model's name were not read. The GFF4 and engine string sections above were added for the next one.
- **2026-10-03 06:18:53, the same parse, with what set it off** (DAOLib issues #3 and #9). In Lothering, the first round of a turn-based fight, the hero threw an Acid Flask at a refugee. A script applied an effect, the effect's event ran a script (through both plugins' event hooks, `dao::events`, nested as their copies chain), and that script's `EffectVisualEffect` loaded the effect's model. An access violation at `0x004D53B4` in `0x004D53A0`, reading `0x24`: the GFF reader on the stack had a null buffer pointer (`EDX = [ECX] = 0`), so a struct template was looked for at 0 + index × 16 + 0x1C. In the first crash the same kind of read found -10.0 where an offset should be. So both times the model's bytes were not there when the parse ran: a resource not yet loaded, or let go, is the likeliest reading, not yet proven. An MMH of 6522 bytes was on the stack, address space 2045 of 4096 MiB in use. The log ended after STACK, before the sections meant to name the model: its own scan read a guard page (issue #9, below).
- **2026-10-03 15:10:07, the same fault, and the model named** (DAOLib issue #3). In the Circle Tower's first floor, round 3 of a turn-based fight at three times speed; the same frames, from `VfxManager::Place` down. This log was whole (issue #9's fix in), and named the model: `fxa_fire_imp_s_c.mmh`, a fire impact, its file being read (7334 bytes on the stack, an MMH, root `mdlh`) and `creature_core` in a frame above. The game's own file, from `modelhierarchies.erf`, is 7334 bytes and reads whole with DAOLib's reader: `MMHName` and the mesh's name set. The bytes on the stack, copied after the fault, read only the empty `MMHFacialAnimationBlueprintName`: they were not the file's.
- **Why, read 2026-10-03: two loads reading one archive's file at once.** The fault is in the model loader's parse (`GraphicsStructures::LoadModelHierarchy`, `0x005968B0`, then `0x00596830`): its view of the bytes (`0x004D5360`) is zeroed when the header's data offset (+0x18) is 0 or past the size, nothing after checks it, and `0x004D53A0` then reads `0x24`. So the bytes began "GFF V4.0" but were not this model's. A resource's bytes are read by `ECResMan::ReadRequestTask::Run` (`0x004E9E20`): it seeks the archive's file to the resource's offset (`ECFileAccess::FileAccess::Seek`) and reads at the file's position (`FileAccess::Read`, a `ReadFile` with no OVERLAPPED). An `ErfSource` hands every task the one file it opened (its +0xB8), and `Run` holds only its own load's lock: a load asked for now runs on the asking thread under the source's lock, a queued one on a worker under none of it. So one load seeking between another's seek and its read hands the other the bytes at its own offset. Another model's GFF, its data offset past the size the parse was given, is this crash; bytes that are not a GFF lose the model quietly. The diagnostic loaders on the branch caught both halves in play: the fire impact (`fxa_fire_imp_s_c.mmh`) and the fireball's impact model (`fxa_fireball_imp_p.mmh`), three slots apart in `modelhierarchies.erf`'s array, read for the first time in the same millisecond on two threads, one of them handed its own buffer, its right size, and bytes that were not a GFF and stayed so. Hooks on every other way a parse's bytes could change (read twice, swapped, freed, destroyed, moved in their array, their source closed) stayed silent through those sessions. Read with the address library's session; the 15:12:53 crash through a null vtable is the same wrong bytes taken further. The portrait reading was ruled out by test 1, and a file still streaming in by the state, which was "loaded".
- **The fix** (`src/fix/ArchiveRead.{h,cpp}`, put in by the loader before the plugins load): inside `Run`, the seek only says where, and the read is a `ReadFile` with an OVERLAPPED carrying the offset, on these synchronous handles a positioned read that shares nothing. The first such read of a session is an info line in `loader.log`, and each time two loads overlap on one file a warning. Seen in play 2026-10-03, the fix alone (the hunt's guards and observers taken out, the turn-based plugin's own portrait workaround off, three times speed, enemy portraits on): the Circle Tower's fire fight eight times over without a crash, where it had crashed four times in six before. The fix is in the engine's path (9,026 archive reads in one fight, on two threads, all through it), and the fire pair's two reads of one archive came within 190 µs on two threads, each read taking 17 to 58 µs. Two reads meeting with the fix in, seen at 17:33:20 on master (16c6146), the fire fight's second run in its process: "file 0x187deec0: thread 52480 seeks it while thread 74296 is between its seek and its read; each reads at its own offset (1 so far)", the fire pair's archive, the frame's thread against a worker. The fight ran to its end and the game on. One meeting in ten fire fights on the fix, a rate well under the hunt's loaders, whose own load-now lookups made more.
- **2026-10-11 11:56:27, a screenshot** (DAOLib issue #78). An access violation at `0x008E24FA`, the exe's `memcpy`, reading `0x4FCA6000` with its source at `0x4FCA5D60` and 0x400 for its length, called from `0x00A23D3F`: `Renderer::ThreadedGraphicsDriver`'s slot 84, which records for the render thread that an object is to be saved to a file. It copies the file's name into the command as a fixed 0x400 bytes from the `std::wstring`'s buffer whatever the string's length, and its slot 85 does the same; they are the exe's only two copies of that length. In the engine's own pools the kilobyte after a short name was other memory of the pool. With the engine's memory on the system's heap (`src/perf/EngineHeap`, issue #69) the name was the last thing before a page that is not there. Eluvian's screenshot had asked the game for its own (`TakeScreenshotMessage`, no name of Eluvian's in it), so the screenshot key goes the same way. **The fix** (`src/fix/SavedFileName.{h,cpp}`): both slots detoured, and the name handed on as a string of the loader's own whose buffer is the 0x400 bytes the copy takes, the name at its start and nothing after.
- **2026-10-12 17:55:33, the mouse in use** (DAOLib issue #105). An access violation at `0x008803A6` reading `0x8109D000`, with `EAX 0x8109CFF4` and `EDX 0x8109CF90`, five minutes into a game with the shaders' plugin, on the frame's thread under `PeekMessageW`. `ECInput::RawInputWin32::ReadMouse` (`0x0087FF40`) asks DirectInput how many buffered records the mouse has, allocates that many of 0x14 bytes, reads and walks them, and then makes the movement's event for each axis from the time stamp and sequence of the record at the count: one past the last, 8 to 16 bytes past the block when every record asked for came. Here five records at `0x8109CF90` ended 12 bytes before a page that was not there. In the engine's own pools that read found other memory of the pool, so the vanilla game has a movement event with a time that is whatever lay there, and no crash. **The fix** (`src/fix/MouseRecords.{h,cpp}`): the four reads' displacements made 0x14 less, a byte each, which is the last record's fields; the code is checked against what was read before a byte is written, and is the same in the three builds. Seen 2026-10-12 in GOG's game: the four bytes as corrected in the running process, and the game played on. Not seen: a hand on the mouse in a corrected game. **Not explained:** the heap's own catch of a read past a block's end (`src/perf/EngineHeap`, issue #78) was in and let this read through. A scan of a running game found every block of the heap's near an end of committed memory followed by reserved memory, which that catch can commit; twelve million allocations of the game's kind outside the game gave no block that close to a page that was not there. So the heap now says in `loader.log` when it finds such a read and cannot make the page, and the crash log says what the address space held at a fault (above): the next one will show which way it fell through.

## Crashes not yet explained

- **A material's texture at a bad address, after an encounter's exit** (DAOLib #40). 2026-10-08 20:33:32, the turn-based mod's session: an access violation reading `0xBD9400CC` at `0x008698A0` (`D3DDriver::D3DGraphicsDriver` slot 72), on the frame thread, under `Graphics::MaterialTextureParam`, `MaterialPass`, `MaterialObjectInstance`, `ObjectNodeMesh`, the renderer's submission queue and umbra's visibility pass; the plugins only as the frame callback passing through. 13 s after the party used a random encounter's City Map exit (`den921ar_wide_1`). The first in hundreds of area changes. A leaving area's texture freed under an object still drawn would fit; one log does not show it.
- **A mesh drawn with a material that has no technique** (DAOLib #149). 2026-10-17 06:02:28, a test copy with elgarashaders' working copy: an access violation reading `0x00000022` at `0x0047119B`, in `FUN_00470eb0`, which groups the draw list by technique and reads each one's +0x22 unchecked. EAX was 0: the material's `Graphics::MaterialSemantic` had no technique at +0x24, which `0x005073C0` leaves null when none of the material's techniques validates (`0x00506E40`, every pass valid on the device), or which is still the constructor's 0 before it is resolved. A shader refused by the device, or a draw during the save's streaming, would fit. The same save twice with the same plugins did not crash, and no shader was refused.
