# Crash logs

The loader (`src/loader/CrashLog.cpp`) installs a crash logger before anything else runs. On a crash anywhere in the game's process, it writes `crash-<date>-<time>.log` beside the other logs, in `Documents\BioWare\Dragon Age\daolib\` (under OneDrive on this machine), and puts a line pointing to it at the end of `loader.log`. Built 2026-09-30, on the shape of Skyrim's CrashLoggerSSE.

## What a log holds

| Section | What |
|---|---|
| Header | The exe's link stamp, whether it is the build DAOLib knows, the time |
| Unhandled exception | The code by name, the address and what it is, for an access violation the address read or written, and the first bytes of code at the fault |
| SYSTEM | Windows, physical memory, and the process's address space. DAO is 32-bit, so address space runs out long before memory does. |
| PROBABLE CALL STACK | dbghelp's walk of the crashing thread. Exact through our DLLs and Windows, with file and line for ours. It can stop early in the game's own code, which has no frame data. |
| RETURN ADDRESSES ON THE STACK | Every value in the stack's first 64 KiB that is a return address into any module (`dao/core/CallSite.h`), the first 128 of them (64 until 2026-10-02, which stopped one crash's list a frame short of the caller that mattered). This keeps going where the walk stops: the game's callers, innermost first. A few may be stale values from earlier calls. |
| REGISTERS, STACK | Each value annotated: code by its module and function, an engine object by its RTTI class (`(CCCreature*)`), a string (`char*` or `wchar_t*`), or a small number |
| GFF4 FILES ON THE STACK | A stack value in the first 64 KiB that points at a GFF4 file's bytes: a file the game is reading. Its length is the word after it (the game passes a file's bytes so) or else as far as the memory goes; a copy is parsed (`dao/core/Gff4.h`) and the line gives the file's type, its root's template and the root's strings by label (`dev/gff4_fields.csv`). For a model that is `6000`, `MMHName`, the model's name. |
| ENGINE STRINGS IN THE STACK'S FRAMES | The engine's `std::wstring`s lying in the stack's first 64 KiB (`dao/core/StackText.h`): a function's own strings, the name of the file or object it is loading among them. Each text once, innermost first; some are left over from earlier calls. |
| MODULES, DAOLIB PLUGINS | Everything loaded, with its range; our plugins |
| LAST LINES OF ... | The last twelve lines of every DAOLib log |

Names come from three places:
- **Our DLLs:** their PDBs, which `tools\deploy.ps1` copies beside them.
- **Windows DLLs:** their exports.
- **The game:** `bin_ship\daolib\functions.tsv`, Ghidra's function list, which deploy also copies (`dev/PROBE.md` says how to export it). With it, `0x0073D054` reads as `FUN_0073d000+0x54` or `GameModeGUI::vfunction7+0x1c`. Without it, the game's addresses stay bare. The names are of the GOG build's addresses. In the EA app's build (`dev/BUILDS.md`) an address in the game is given as that build's own, then as GOG's, by which the name is found: `DAOrigins.exe 0x004c1770 (GOG 0x005d6740) CClientExoApp::SetPaused+0x0`, or `(not in the GOG build)` for code EA's build alone has. Written 2026-10-01 and not yet seen: no crash has been made in the EA game.

## Hang logs

A stall that ends leaves no crash log, so the loader also keeps a watchdog (DAOLib issue #4, for a 32-second stall in a turn-based fight, 2026-10-03). It counts frames with `dao::OnFrame` and checks once a second from a thread of its own. When no frame has come for 5 seconds (`DAOLIB_HANG_SECONDS` in the game's environment; 0 turns it off), it writes `hang-<date>-<time>.log` beside the crash logs:

- **A sample.** The frame thread is suspended for as long as it takes to copy its registers and its stack's first 64 KiB, and nothing is allocated meanwhile, since the thread may hold the heap's lock. The log is written from the copy while the game runs on: the registers, the return addresses, the stack, the GFF4 files and engine strings on the stack, as a crash log has them. There is no call stack walk, since dbghelp would walk the live thread. Memory the stack points at, a file's bytes or a string's heap text, is read after the thread is let go, so it may have changed.
- **What the game was doing.** Each sample says the game's mode, and whether its window was in front, not in front, or what Windows calls not responding.
- **While it lasts.** Another sample every 5 seconds, twelve at most. A sample whose return addresses match the one before is a loop or a wait; one that differs is the thread making slow progress.
- **The first sample** also has the system, the modules, the plugins and the last lines of every log, what led into the stall.
- **The end.** When frames come back, the last line says after how long. `loader.log` says when a hang log was begun and when frames came back.
- **Reading what the stack points at.** Both logs follow every stack word that looks like a pointer, and some point into a thread's stack guard page. Reading one raises `STATUS_GUARD_PAGE_VIOLATION`, which `dao::TryCopy` does not catch (`tests/test_saferead.cpp`). A crash log on 2026-10-03 ended mid-way that way (issue #9). Every such read now asks `VirtualQuery` first, region by region, and goes ahead only where the pages are committed, readable and not guards (`dao/core/Pages.h`).
- **When not.** Before the game has a mode, while loading and at the main menu's start-up, where frames may stop by design. Not with the window minimised, or gone, as the game closes.
- **Seen in play**, 2026-10-03, in the turn-based playthrough (GOG): from 01:28 on, through four launches and three quits, five loads (two from inside a fight), two area transitions, a skipped cutscene, the Store screen and some six fights of up to 19 rounds, it wrote no hang log: none at launch, at exit, in a load or in a menu, and no stall came. The game was in front throughout, so whether frames stop with it behind another window is not yet seen. A real stall's log is not yet seen either.

## How it stays installed

It is an unhandled-exception filter, and the game's C runtime installs one of its own at start-up. So the logger also detours `SetUnhandledExceptionFilter`. A filter the game sets afterwards is remembered and called after ours, so the game's own handling still happens, and Windows Error Reporting still records the crash. The log is written on a new thread, because the crashing thread may be out of stack. The crashing thread waits up to a minute for it.

## Testing it

With `DAOLIB_PROBE_CRASH_TEST=1` in the game's environment, the probe crashes on purpose on the game's thread, in the first `SetPaused` at start-up. Start the game with the variable set only for that run:

```powershell
$env:DAOLIB_PROBE_CRASH_TEST = '1'; Start-Process "...\bin_ship\DAOrigins.exe" -WorkingDirectory "...\bin_ship"; Remove-Item Env:DAOLIB_PROBE_CRASH_TEST
```

The log from that test (2026-09-30) named `CrashIfTesting` at `Probe.cpp:63`, the hook at `Probe.cpp:87`, the engine's `FUN_005DD310` below it, and the chain down to `Eclipse::UpdateTask` on a `Multithreading::Thread`.

## The crashes it has explained

- **2026-09-30, the probe's queue hook.** `strnlen` in `dao::DecoratedTypeName`, reading `0x84C6CF93`. Its check that a pointer lies inside the exe's image computed `end - address` without first checking `address < end`. An address above the image wrapped the subtraction around and passed. A command object's garbage word took that path. The check is now `dao::core::Contains` (`tests/test_range.cpp`), and the crash before it, in `memcpy`, was almost certainly the same bug.
- **2026-09-30, a creature's properties.** An access violation reading `0x14` at `0x006436EB`, in the engine's property getter, called from `dao::CCCreature::Property` in the example plugin's frame callback; the log named `ESI` a `CCCreatureStats*`. The getter was given the creature's stats, but `GetCreatureProperty` gives it the stats' property list, 0x190 bytes in (`lea ecx, [eax + 0x190]` at `0x0066D002`). On the stats themselves it read another vector, whose entry for strength was `0x104FF`, and called through it. The register naming the class was the clue that the object was right and the offset wrong. `Property` now adds 0x190; the setters take the stats and add it themselves (`0x0071B239`).
- **2026-10-02, an effect's model as a turn-based fight began** (DAOLib issue #3). An access violation at `0x004C24D7` in `std::wstring(const wchar_t *)` (`0x004C2480`). The engine was parsing a model hierarchy (`GFF V4.0PC  MMH V0.1`, 7566 bytes, on the stack) and read `MMHName` (6000) of an emitter group's node (`0x00591070`) from a place that held the float -10.0, as a string's offset. The return addresses lead from the model blueprint loader (`GraphicsStructuresManager` slot 40) up through the graphics layer to `VfxManager::Place`+0x39: the effect's model was loaded as the effect was placed, synchronously on the game's main thread. The turn-based mod's log has no preview in that run, so the `Place` was the game's own. A replay of the same steps passed, and the file's header was intact, so the bytes or the parse's position were different that once: memory changed under the parse is a guess, not read. The log could not say which model: the return-address list stopped at its cap of 64 at `Place`, and the buffer and the model's name were not read. The GFF4 and engine string sections above were added for the next one.
- **2026-10-03 06:18:53, the same parse, with what set it off** (DAOLib issues #3 and #9). In Lothering, the first round of a turn-based fight, the hero threw an Acid Flask at a refugee. A script applied an effect, the effect's event ran a script (through both plugins' event hooks, `dao::events`, nested as their copies chain), and that script's `EffectVisualEffect` loaded the effect's model. An access violation at `0x004D53B4` in `0x004D53A0`, reading `0x24`: the GFF reader on the stack had a null buffer pointer (`EDX = [ECX] = 0`), so a struct template was looked for at 0 + index × 16 + 0x1C. In the first crash the same kind of read found -10.0 where an offset should be. So both times the model's bytes were not there when the parse ran: a resource not yet loaded, or let go, is the likeliest reading, not yet proven. An MMH of 6522 bytes was on the stack, address space 2045 of 4096 MiB in use. The log ended after STACK, before the sections meant to name the model: its own scan read a guard page (issue #9, below).
- **2026-10-03 15:10:07, the same fault, and the model named** (DAOLib issue #3). In the Circle Tower's first floor, round 3 of a turn-based fight at three times speed; the same frames, from `VfxManager::Place` down. This log was whole (issue #9's fix in), and named the model: `fxa_fire_imp_s_c.mmh`, a fire impact, its file being read (7334 bytes on the stack, an MMH, root `mdlh`) and `creature_core` in a frame above. The game's own file, from `modelhierarchies.erf`, is 7334 bytes and reads whole with DAOLib's reader: `MMHName` and the mesh's name set. The bytes on the stack, copied after the fault, read only the empty `MMHFacialAnimationBlueprintName`: they were not the file's.
- **Why, read 2026-10-03: two loads reading one archive's file at once.** The fault is in the model loader's parse (`GraphicsStructures::LoadModelHierarchy`, `0x005968B0`, then `0x00596830`): its view of the bytes (`0x004D5360`) is zeroed when the header's data offset (+0x18) is 0 or past the size, nothing after checks it, and `0x004D53A0` then reads `0x24`. So the bytes began "GFF V4.0" but were not this model's. A resource's bytes are read by `ECResMan::ReadRequestTask::Run` (`0x004E9E20`): it seeks the archive's file to the resource's offset (`ECFileAccess::FileAccess::Seek`) and reads at the file's position (`FileAccess::Read`, a `ReadFile` with no OVERLAPPED). An `ErfSource` hands every task the one file it opened (its +0xB8), and `Run` holds only its own load's lock: a load asked for now runs on the asking thread under the source's lock, a queued one on a worker under none of it. So one load seeking between another's seek and its read hands the other the bytes at its own offset. Another model's GFF, its data offset past the size the parse was given, is this crash; bytes that are not a GFF lose the model quietly. The diagnostic loaders on the branch caught both halves in play: the fire impact (`fxa_fire_imp_s_c.mmh`) and the fireball's impact model (`fxa_fireball_imp_p.mmh`), three slots apart in `modelhierarchies.erf`'s array, read for the first time in the same millisecond on two threads, one of them handed its own buffer, its right size, and bytes that were not a GFF and stayed so. Hooks on every other way a parse's bytes could change (read twice, swapped, freed, destroyed, moved in their array, their source closed) stayed silent through those sessions. Read with the address library's session; the 15:12:53 crash through a null vtable is the same wrong bytes taken further. The portrait reading was ruled out by test 1, and a file still streaming in by the state, which was "loaded".
- **The fix** (`src/fix/ArchiveRead.{h,cpp}`, put in by the loader before the plugins load): inside `Run`, the seek only says where, and the read is a `ReadFile` with an OVERLAPPED carrying the offset, on these synchronous handles a positioned read that shares nothing. The first such read of a session is an info line in `loader.log`, and each time two loads overlap on one file a warning. Seen in play 2026-10-03, the fix alone (the hunt's guards and observers taken out, the turn-based plugin's own portrait workaround off, three times speed, enemy portraits on): the Circle Tower's fire fight eight times over without a crash, where it had crashed four times in six before. The fix is in the engine's path (9,026 archive reads in one fight, on two threads, all through it), and the fire pair's two reads of one archive came within 190 µs on two threads, each read taking 17 to 58 µs. Two reads meeting with the fix in is not yet seen.
