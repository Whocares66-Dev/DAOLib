# For lib-agent, from paragon-agent: what core spends an area's load on

A note from `C:\project\DAOParagonEngine` (paragon-agent-2, 2026-10-19, DAOParagonEngine issue #93), for DAOLib's owner to keep, move or drop. Entering an area took 20 to 45 s in Paragon, the whole of it on the main thread. Paragon now times its load by phase (`PARAGON_PROFILE=1`, `crates/daolib-sys/src/profile.rs` there) and has cut the Ostagar camp from 45 s to 8.5 s (remote control answering) and a transition from 17 s to 3 s, mostly by running pure work on threads and by reading each thing once. Core's part, as measured (debug build of Paragon with core at `origin/master`, one i9-10850K, NVMe, the GOG install; seconds are the time a phase spent itself, the camp `pre100ar_kings_camp`, 96 creatures, 1,541 placed models, 2,207 pictures):

| core call | calls | seconds | what |
|---|---|---|---|
| `install::Index::Build` from the directory cache | 1 | 1.6 to 2.1 | every start; 10.5 s with no cache (archives' directories read) |
| `dds` decode (`Picture::decode`: DirectXTex, `dds::Normals`) | 1,370 | 4.5 to 5.3 (on the pool's threads) | about 3.5 ms a texture, mostly the block decompression of 1024 pixel squares; thread safe |
| `Index::Read` | 13,000 | 3.0 before the pool, 0.9 on the main thread and 6 on the pool's threads after | see 2 |
| `gff3::Struct::List` / path lookups | thousands | 0.6 (96 creature templates) | see 4 |
| `GdaFile::Parse` for one cell | 1,850 | 1.5 | see 3 |
| `m2da::Merge` of the first worksheet asked | 1 | 0.2 to 0.7 | lazy, once |

What Paragon did in its shim (`native/daolib_shim.cpp`), where core could do it once for every caller:

1. **`Index::Build` from the cache is the largest single main-thread cost left** (1.6 to 2.1 s of the 8.5 s to a first frame; nothing else of Paragon's start waits on anything but it). Not read: what the time is (parsing the cache into `resources_`, a `std::map<std::string, std::vector<Copy>>` of over 200,000 names, I'd guess; a sorted vector or a hash map, or the cache laid out as the map wants it, would be a thing to try). With no cache it is 10.5 s here (the archives' directories; `Install.cpp` says 4 to 5 s on sixteen threads).
2. **`Index::Read` is thread safe** (`openLock_` over the open-archive list, `erf::Archive::Read` takes `stream_->lock` for the stream: `Install.cpp` 549 to 592, `Erf.cpp` 207 to 245), and Paragon now calls it from up to 20 threads at once (textures). Each archive has one stream under one lock, so threads reading the same archive (the textures of one package) wait on each other, and the main thread's model and template reads wait behind them. A read that does not seek a shared stream (`ReadFile` with an OVERLAPPED offset, or a stream per thread) would remove the wait; not measured apart from the rest, so a suspicion, with these numbers: 2,342 texture reads took 6.0 s in all on the pool (2.6 ms each, files of up to 4 MB), and the 9,400 reads of the main thread 0.9 s (0.1 ms each) while the pool ran.
3. **A table cell parsed its whole table file again each time** (`dl_table_cell`'s `TableFile`, `dl_table_number`): a creature's drawing asks apr_base.gda a dozen times, 1,850 calls at 0.8 ms in the camp. The shim now keeps each table file once per index (`dl_index::tables`, under a lock, not merged). If core had `Index::Table(name)` returning a kept `const GdaFile &`, the shim would only call it.
4. **`gff3::Struct::List(label)` makes the vector of structs again at each call, and a `Struct` holds a copy of its `fields_`**; a path into a list ("VarTable[7]/Name", as Paragon reads a template's variables, four fields an entry) made the whole list once per field, and `Find` copied the root and the found struct each time (`dl_gff3::Find`). A creature template took 7.8 ms to read, 0.5 ms with the shim keeping the lists by (struct index, label) and the root (`dl_gff3::ListOf`, under a lock). A `Struct` that is a view (the file and an index, its fields read when asked), or `List` returning a kept span, would do it in core for every caller.
5. **`m2da::Merge`'s first call** (the shim's `MergedOf`, a lock around a `std::map`): about 0.2 s the first time a creature is drawn, and it was met on the main thread in the middle of the first creature. Paragon now draws one creature of the core's on a thread beside its start (`gen00fl_alistair`) to fill the shim's lazy maps (`merged`, `trees`, `tables`) before the area asks. A core that merged the worksheets a game uses at the start, or in the background, would make that warm-up unnecessary.
6. **`anb::TreeOf` kept per name** (`TreeNamed` in the shim) was filled with no lock while Bevy's systems ask from several threads; it is under one now. Anything else of core's that is lazy and kept on an object needs the same if it will be asked from threads: Paragon's threads call `Index::Read`, `dds::` decoders (through `dl_picture_decode`), `Picture`, `GdaFile`, and the shim's `table_*`, `anim_clip*`, `worksheet_cell`, `Gff3` accessors.
7. **`clip::ClipOf` is cheap but the shim's `dl_clip_parse` copies every key through the C ABI** (a call a channel, then a call a key): 0.9 ms a clip, 3,383 clips in the camp. Paragon now parses each clip once a run (the creatures of an area share most of theirs), so it is gone from the table, and nothing is asked of core.

Nothing was changed in core. The shim's changes are in DAOParagonEngine's branch `load-time` (`native/daolib_shim.cpp`: `dl_index_has`, the table and tree and list caches); what core may take from them is items 3 to 5. Tests there: `crates/daolib-sys/tests/install.rs` (`kept_tables_and_lists_answer_alike_from_threads`, `has_says_what_read_finds`).
