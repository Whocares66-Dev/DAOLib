# Builds

Dragon Age: Origins Ultimate Edition is sold by GOG, EA and Steam, all at 1.05.13263.0, and they are not one executable. What each is, how they differ, and where every function and global is in each belongs to the address library, `extern\DAOAddressLibrary` (its `dev\BUILDS.md`). This is how DAOLib works in more than one of them. Read 2026-10-01 ([issue 1](https://github.com/Whocares66-Dev/DAOLib/issues/1)).

| Build | State |
|---|---|
| GOG | The one everything was read in: the Ghidra project, the names, every address in a comment. Verified in play. |
| EA app | Known to the address library. Seen in play 2026-10-01 with the loader put in from the build tree ("Seen in play"), and since run deployed, where it works (the user, 2026-10-12: "we did test it. it works w/ ea"). On this machine the EA app otherwise starts Steam's copy, since `HKLM\SOFTWARE\WOW6432Node\BioWare\Dragon Age` has `Path` = Steam's folder (`Flavour = steam`; the play tester, 2026-10-10), a machine-wide key that is the user's to change. |
| Steam | `steam-1.05`, read 2026-10-01 in the address library (its `dev/STEAM.md`): GOG's code byte for byte, every GOG ID at its GOG address, wrapped by SteamStub 2.1, and with GOG's link stamp. Below. |

## IDs, not addresses

The library does not hold addresses. It holds IDs: numbers the address library gives, one for every function and global of the game, that mean the same thing in every build. `dao/Addresses.h` is rows of them, and at run time each is looked up in the file for the build that is running.

```cpp
DAO_ADDRESS(kCClientExoApp_SetPaused, 10547)
```

The row is the ID and nothing else about the function. What the engine calls it (`CClientExoApp::SetPaused`) and where it is in each build (`0x005D6740` in GOG's, `0x004C1770` in EA's) are in the address library's table, `extern\DAOAddressLibrary\data\addresses.csv`, and only there: one name for a thing wherever it is spoken of, and no address the code uses written twice (the comments in `Addresses.h` still tell their stories in GOG's addresses, for reading against Ghidra). `python tools\address_ids.py 10547` says them, with what the library notes about the ID in each build, and takes a constant, an address of GOG's or part of a name as well. `tools\names.py` gives the table's names to the Ghidra project.

- **Adding one.** Read the address in GOG's Ghidra project as before, and write the row as it was read: `DAO_ADDRESS(kName, "Engine::Name", 0x005D6740)`, or `DAO_VFTABLE(0x00B007D0);` inside a message class's struct. Then run `python tools\address_ids.py`: it finds the ID, writes the name into this checkout's copy of the address library's table (a vftable has its from the exe's RTTI), leaves the row as the ID alone, and says if the ID is `changed`, `shared` or `ambiguous` in a build. The name is a change to the address library, which is kept by its own session and not committed to from here: send that session the line the tool prints, and when it has committed the name, check its commit out in the submodule and commit the submodule with the row (`tools\address_ids.py`'s head has the steps). Until the tool has run the row does not compile, and a ctest fails on one left over.
- **An address with no ID.** IDs are for what something refers to: a function's start, a global. A place inside a function is that function's ID plus an offset; the tool says which. In a function the address library marks `changed` in a build, an offset into it is GOG's, and may be wrong there (`dao::Module::Find`).
- **At run time.** `dao::Module::Address(id)` is the address in the running process, zero where the running build has no such thing; `dao::At` gives a null pointer for that and `dao::Detour::Attach` refuses it. `dao::Module::Preferred(runtime)` goes back to GOG's address, so the logs, the probe's call chains and the crash logger's names read the same whichever build ran.
- **The generated tables.** The message handlers (`dao/generated/MessageHandlers.h`) and the probe's census list are generated with IDs from the same table; the script commands need none, since the engine's own table gives their functions at run time.

## The files

The address library's build packs its table into one file per build of the game, `daoaddresses-<link stamp>-<image size>-<entry rva>-<base>.bin`, in `build\<preset>\daolib\addresses\`. `tools\deploy.ps1` puts them in `bin_ship\daolib\addresses\`, beside the plugins. The loader and each plugin read the one named for the running exe's four header fields (`dao::Module::Build`), and check that the header inside says the same (`dao::Module::Library`). All four, since Steam's build has GOG's link stamp. The library wrote GOG's and EA's files under their first names too, by the link stamp alone, until its ae992b3; nothing reads those now, and `tools\deploy.ps1` removes any it finds in a game's folder.

**The address library has releases of its own**, the first 0.1.0 on 2026-10-10 (its tag `v0.1.0`): one zip, `DAOAddressLibrary-<version>.zip`, of these files in this folder, with its `README.txt` and `LICENSE.txt` inside the folder so that they do not land on DAOLib's at the root. DAOLib's zip (`tools\package.ps1`) keeps its own copies, so a player with DAOLib alone has a working set. The other zip is for the time between DAOLib's releases: a plugin built on a newer table than the player's DAOLib came with, or a build of the game the library came to know since. Newer files serve every older loader and plugin, since the table never loses an ID or an address, so a plugin's page asks for "Address Library x.y.z or later". There a patch is the same files knowing more, a minor a file for another build of the game or an addition to the reader, and a major a new `format` word: a loader built before it refuses such a file and loads nothing, so a major goes out together with a DAOLib that reads it. None is planned.

A DAOLib release holds the submodule at one of those tags, and `package.ps1` writes which into the zip's `README.txt`; at any other commit, as between releases, it writes the commit and warns, and `release.ps1` refuses (`dev/RELEASING.md`). `deploy.ps1` keeps a file already in the game that knows more IDs than the build's. Extracting a zip cannot, so an older DAOLib extracted over a newer Address Library puts older files back: the `README.txt` says to extract the Address Library again after it, and that the loader's "address library: N IDs for this build" line is the check, N never falling from one release to the next (DAOLib #54). One thing no release relies on: the first folder `Module.cpp` looks in is `daolib\addresses` beside the module itself, which for a plugin is inside its own folder, so a plugin that shipped address files there would read its own before the shared ones. None does.

**A build with no file is a build nothing is done in**: the loader logs which file it wanted and loads no plugin. So which builds the library works in is not compiled into anything. A new build of the game needs a new file in that folder, and neither the loader nor a plugin rebuilt. The GOG build's file goes with the others whichever build is installed, since `Preferred` reads it.

`LoaderInfo::knownExecutable` says whether there is a file, and `kPluginApiVersion` is 2: a plugin built against 1 holds addresses, and the loader's version check refuses it.

## What an ID cannot do

All in the address library's `dev\BUILDS.md`; what matters to a plugin:

- **A field offset is not an address.** Three classes are laid out differently in EA's build: `ContentManager` (0x10 bytes inserted at +0x17C), `GUI::ScaleformManager` (0x10 inserted at +0x190) and the `AnimBaseWield`/`AnimBaseParts`/`AnimBaseHead` family (fields at +0x224 and up 0x10 lower). The library reads `GUI::ScaleformManager` at +0x18, +0x44, +0x70 and +0xA8 (`dao/Gui.h`), all below the insertion, and none of the others. A field added for one of these needs an offset per build.
- **98 functions are not the same code in EA's build**, the DLC's online check among them. A detour at the start of one still catches it. Of what the library names, `GUI::ScaleformManager::Initialize` is one.
- **Identical functions are folded differently by each build's linker.** A detour on a small generic function (a getter, a destructor) catches a different set of callers in each build. Of what the library names, `std::wstring::~wstring` and the vftables of `SmartData::Attribute<int>` and `<bool>` are such, none of them hooked.

## The loader in a wrapped build

EA's exe is wrapped: `.text` and `.data` are encrypted on disk, and its entry point is a jump into `Core\Activation.dll`, which checks the licence, decrypts them and goes on to the game's own entry point. The headers in memory stay the file's, so the address library's file for the build carries the wrapper's entry point, and the game's own is an ID like any function (`dao::addr::kEntryPoint`).

In GOG's build the loader detours the entry point from `DllMain` and loads the plugins there. Where the entry point in the headers is not the game's, that is a wrapper's jump, the game's code is still encrypted, and a plugin's hooks would be written into bytes about to be decrypted over. There the plugins load at the first call out that the game's own code always makes: the CRT's start (`__tmainCRTStartup`, 0x008E2E44, what the entry point jumps to) asks for the process's startup information before anything else, so the loader detours `GetStartupInfoA` and loads the plugins the first time its caller is inside the exe's `.text` (0x008E2E5E in GOG's listing). That is the same moment as GOG's, a call later, on the same thread.

**Not the clock, which it waited on until 2026-10-12** (DAOLib #94). The entry point's first call sets up the stack cookie (`__security_init_cookie`, 0x008F4907), and that reads the clock only for a cookie still at its default, 0xBB40E64E. Windows sets a cookie itself as it loads an image whose load configuration names it, and all three builds' name it. In Steam's file `.data` is as GOG's, the cookie at its default, so Windows had set it, the CRT read no clock, and the first read from `.text` the loader saw was at 0x008E21BB, in the game's `time()` (0x008E21AC, thirteen callers), well into its start: after its static constructors and the engine's first allocations. So in Steam's game the plugins loaded late, and the engine heap (DAOLib #69), which goes in before the first allocation or not at all, never went in: `engine heap: the engine's memory manager is already there`. In EA's file `.data` is encrypted, the cookie's bytes there are not the default, Windows leaves them, and the wrapper's decrypting puts the default back: there the CRT read the clock (0x008CAC01) and all was in time. What these notes say below of "the clock read from" a place is of the loader before this; Steam's 0x8e21bb was never the CRT's first call.

Seen with `GetStartupInfoA`, 2026-10-12: Steam's game, `its startup information asked for from 0x8e2e5e` 0.2 s after the loader came in, `the engine's memory is the system's heap`, then with `examples\resume` a save loaded in 4 s and a minute in the world, 2,912 frames, the probe's checks agreeing, no crash or hang log; and EA's and GOG's games through `tools\play_matrix.ps1` (`dev/TESTING.md`). The loader does not know EA's build by name: it knows a wrapped one by its entry point.

`daorigins.exe` started by anything but the EA app decrypts nothing: it asks the EA app to start the game and exits. That run never gets there, and loads nothing.

The loader looks for `daolib\plugins` (a folder per plugin) and `daolib\addresses` beside itself, which deployed is beside the exe.

## Steam

Read 2026-10-01 in the address library (`extern\DAOAddressLibrary\dev\STEAM.md`), from the install at `E:\SteamLibrary\steamapps\common\Dragon Age Ultimate Edition\bin_ship`. Unwrapped, Steam's exe is GOG's: the whole `.text` is the same bytes, and every one of GOG's IDs is at its GOG address, so nothing here reads differently in it. What differs is the wrapper, SteamStub 2.1: `.text` is encrypted on disk, a section of its own (`.bind`) holds the stub, and the headers' entry point is the stub's (`0x9ed2ee`, image size `0xa49000`). And the link stamp is GOG's, `0x4eb19d53`, which is why the address files are named by all four header fields (above).

The loader needs nothing of its own for it. Its test for a wrapped build, the entry point's ID against the headers' entry point, says wrapped, and it waits for the game's own code's first call, as in EA's build.

**Started once, 2026-10-01 23:18**, by the session that read the address library's Steam column at the user's request, from a DAOLib worktree of its own with the same changes (`C:\project\DAOAddressLibrary\game\daolib-steam`, branch `feat/steam-platform`), deployed into the Steam folder with the probe and two examples. `loader.log`:

- `DAOrigins.exe at 0x400000: link stamp 0x4eb19d53, image size 0xa49000, entry rva 0x9ed2ee`: the stub leaves the headers in memory as they are on disk.

## GOG's exe is started on two processors (2026-10-12, DAOLib #89)

GOG's `DAOrigins.exe` carries a process affinity mask of 3 in its PE load configuration (the image's `ProcessAffinityMask`, at file offset 0x75A130): Windows starts every copy of it on the machine's first two logical processors, whatever started it and before any of its code runs. EA's exe and Steam's carry 0 there, and are started on every processor. So it is GOG's doing, not BioWare's; why is not written anywhere we have. The game's thread manager (`Eclipse::DAThreadManager`, its start-up at 0x004017D0) counts the processors the process was given and makes that many worker threads less one, a multi-threaded renderer with two or more, and sets a mask itself (1) only in its single-core mode.

One copy is then as GOG meant it. Several copies (the instances of DAOLib #67) share those two processors, some sixty threads each, while the rest of the machine idles: seen on ten cores of two threads with three and four copies, the machine's CPU under 20% and each copy's frame thread stalling for seconds in a yield loop on its own task threads (seventy hang logs in one instance's day). What set the mask was found by elimination: nothing in the launch path or the plugins, no call of `SetProcessAffinityMask` after start (the probe detours it), no compatibility flag, and a bare copy of the exe under another name in an empty folder came up at 0x3 as well.

The loader gives the process the machine's processors before the game's code runs (`src/perf/AllProcessors.h`; `DAOLIB_ALL_PROCESSORS=0` leaves it out), which is what EA's and Steam's builds have from the start: the thread manager counts them and makes its worker threads, and Windows puts each thread on a processor that is free. The game pins no thread of its own. Seen in play the same day: a copy on 0xfffff with 80 threads where it had 57, 60 frames a second in the world, in a fight and after a change of area, a second copy started beside it with the first's longest time without a frame 18 ms; and by the multiplayer mod's session, four copies in one session through a fight of 193 seconds, 60 frames a second in every copy throughout, no hang or crash log, the four games agreeing on every creature. A long session has not been seen.

It was first answered another way (DAOLib #89, the same day): each copy kept on two processors and moved to a pair no other copy had, with an enumeration of the other copies and a rule for choosing among pairs. That worked round the mask and kept it, and was replaced within the day by the above (DAOLib #92; the user: "do the simplest, most obviously correct thing"). What was seen with it stands as the measure of the fault. A save loaded in a copy beside three others at 0x3: left at 0x3, 34.6 frames a second; on a pair of its own, 58.5. A copy in the world, its frames asked for some twenty times a second, while a second copy started beside it (DAOLib #90): with both left on the first two processors the first answered nothing for 5.7 s as the second began its start-up, not even from its server thread, then went up to 0.9 s between frames for a quarter of a minute more, and the second took 21.5 s to serve where it takes 10; with each on processors of its own, 41 ms. The multiplayer mod's session, two to four copies in one session: 60 frames a second in every copy where three had given the host 17 to 19, and no hang log written where the host's instance had written 85.

## Windows loads its own version.dll first (2026-10-12)

Two players, one with EA's build on Windows 11 (26H2, build 26300.9457) and one with Steam's, reported 0.1.0 doing nothing: the game runs, no mod shows, and `Documents\BioWare\Dragon Age\daolib` is never made. That is the loader not in the process at all. Whether what follows is what they have is not known until they look; it gives exactly that, and it is common advice for this game.

**A compatibility layer on the exe can bring in the system's `version.dll` before the exe's imports are resolved.** Windows loads a layer's shim DLLs from the system folder first, with everything they import, and `AcGenral.dll` imports `VERSION.dll` and `WINMM.dll`. The exe's own import of `VERSION.dll` is then answered by the module of that name already there, and the one beside the exe is never opened. No error, no log. Seen on this machine (Windows 10 19045) with two small 32-bit exes and no game: one importing `version.dll` with 0.1.0's `version.dll` beside it, printing the path of the module it got; one importing nothing, printing which names were in the process at `main`, each run under `__COMPAT_LAYER`.

| The Compatibility tab's setting (layer) | `version.dll`, `winmm.dll` taken from the system first |
|---|---|
| none; high DPI settings (`HIGHDPIAWARE`, `DPIUNAWARE`, `GDIDPISCALING`); 16-bit colour; 640 x 480; Windows XP SP2 to Windows 8 modes | no |
| Disable fullscreen optimizations (`DISABLEDXMAXIMIZEDWINDOWEDMODE`); 8-bit colour (`256COLOR`); `DISABLETHEMES` | yes |

`dinput8.dll`, `netapi32.dll`, `psapi.dll`, `d3d9.dll`, `winhttp.dll` and `d3dx9_36.dll` were in the process under none of them, and are in no shim DLL's imports here (`apphelp`, `AcLayers`, `AcGenral`, `AcSpecfc`, `AcXtrnal`, each with what it imports, read from `SysWOW64`). GOG's installer sets `HIGHDPIAWARE` on its exe, which is why GOG's game here has a layer and loads the loader. Windows 11's shims were not read: this machine has none.

Others have met it: Ultimate ASI Loader's issue 215 (2026-06-29, https://github.com/ThirteenAG/Ultimate-ASI-Loader/issues/215) has the same silence on Windows 11 after update KB5095093, a commenter finding the local `version.dll` passed over with fullscreen optimizations disabled and the loader working as `winhttp.dll`, and another that it came only for games in a store's default folder. So on Windows 11 something may set the layer, or its like, without the player.

**A player's way round it:** on `bin_ship\DAOrigins.exe`, Properties, Compatibility (and "Change settings for all users"), untick "Disable fullscreen optimizations", reduced colour mode and any compatibility mode. `reg query "HKCU\Software\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers"` (and `HKLM`) lists what is set, by the exe's path.

**The loader is `dinput8.dll` since** (DAOLib #93, the same day; `src/loader/Proxy.cpp`). All three builds import it for `DirectInput8Create`, GOG's and Steam's exes themselves and EA's game through its wrapper, and no shim DLL does. Seen two ways:

- **Without the game:** a 32-bit exe importing both DLLs, 0.1.0's `version.dll` and the branch's `dinput8.dll` beside it, under 22 layers and pairs of layers (those of the table, and the Compatibility tab's others). Its `version.dll` was the system's under nine, each one that brings `AcGenral.dll`; its `dinput8.dll` was the one beside it under all 22, and `DirectInput8Create` through it answered `S_OK`.
- **In the game** (GOG's, from the private copy `game\gogrun` as the instance `lib-agent`, with `__COMPAT_LAYER=DisableDXMaximizedWindowedMode` in the environment it was started from, which is the layer the checkbox sets). With `version.dll` beside the exe: the process had `AcGenral.DLL` and `C:\Windows\SYSTEM32\VERSION.dll`, no loader, no log written, Eluvian never answering: the players' report, reproduced. With `dinput8.dll` in its place, the same layer: `AcGenral.DLL` and the system's `VERSION.dll` again, `DINPUT8.dll` from `bin_ship` with the system's behind it, `loader.log` whole (`entry point detoured`, `eluvian.dll: loaded`, `probe.dll: loaded`, `2 plugin(s)`), and the game at its main menu. Without a layer: the same log, no shim DLL. Both plugins were built before the change and loaded as they were: nothing of a plugin knows the loader's name.

- **In Steam's and EA's games,** the branch deployed into each (`deploy.ps1 -Install steam`, `-Install ea`) with the probe, the example and `sparelist`, the layer set as the Compatibility tab sets it (the exe's path under `HKCU\Software\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers`, `~ DISABLEDXMAXIMIZEDWINDOWEDMODE`) and taken out after, each game ended after 40 to 50 s, both installs put back to stock. Steam's: `AcGenral.DLL`, the system's `VERSION.dll`, `DINPUT8.dll` from `bin_ship`; `the game's code is wrapped`, `running, decrypted (the clock read from 0x8e21bb)` 0.3 s later, three plugins `loaded`, no crash or hang log; and the same without the layer. EA's, with the layer: the same three modules, the loader's first line 3 s after the process began (the wrapper resolving the game's imports, `DINPUT8.dll` among them, by name), `the clock read from 0x8cac01` 0.1 s after that, three plugins `loaded`, no crash or hang log. EA's was not run without the layer.

How each was started, for the next such run. Steam's exe started by hand hands off to Steam, which opens the launcher's window and waits for Play; with `SteamAppId=47810` and `SteamGameId=47810` in the environment and Steam running, the stub goes on to the game itself. (The hand-off run had loaded the loader too, and the loader's exit log named the stub's `ExitProcess(0)`.) EA's exe hands off to the EA app, which starts whatever `HKLM\SOFTWARE\WOW6432Node\BioWare\Dragon Age`'s `Path` names: Steam's copy, on this machine, until `Path` was set to EA's folder for the run and put back after (the user's leave, 2026-10-12).

**The engine heap does not go in in Steam's game** (seen in these runs, and the same with master's `version.dll` there, so not the name's doing): `engine heap: the engine's memory manager is already there` at the first clock read, where GOG's and EA's say `the engine's memory is the system's heap`. The pointer is at the same address as GOG's and is zero in both files; issue 69's notes had Steam and EA as not run. It was the loader's cue, which in Steam's game came late, and is mended (DAOLib #94; "The loader in a wrapped build", above).

**Another mod of the same name is chained** (DAOLib #93; a player: "dinput8.dll is already in use by another recent mod, the Controller Support Mod"; the user: "ours can load plugins, we should be the main dinput8.dll. so they rename theirs and we pass through to it"). Two files cannot have the name, so the other mod's goes beside the loader as `dinput8.chain.dll`, and the loader's six exports pass to it where it has them and to the system's where it has not; it passes to the system's as it always did. One, by that one name: each such DLL goes straight on to the system's, so only one can stand behind the loader in the game's calls. One that will not load leaves the system's in its place, with a warning in `loader.log`. Seen with a stand-in for such a mod (a proxy that passes `DirectInput8Create` to the system's, found by its path, and writes a line for each call): in the test exe with no layer, `DisableDXMaximizedWindowedMode` and `Win7RTM`, each call written and `S_OK`, and a file of that name that is no DLL leaving the exe working; and in GOG's game under the layer, `another mod's dinput8.dll is chained` in `loader.log`, the game's own `DirectInput8Create` written by the stand-in with `S_OK`, three plugins loaded, the game at its menu. Not seen with the Controller Support Mod itself, which was not to hand: a DLL that asks for the system's by its bare name would get the loader again.

Not seen: Windows 11, and input through the proxy beyond the games starting. **An install that has 0.1.0's `version.dll` must lose it:** left beside `dinput8.dll` where no layer keeps it out, both loaders are loaded (seen once by accident in Steam's game, master's `version.dll` not yet deleted when `dinput8.dll` went in: both in the process from `bin_ship`, the game at its menu for 30 s; what the plugins made of two loaders was not read). `deploy.ps1` takes the old one out; a zip cannot.

**Not the C++ runtime.** 0.1.0's `version.dll` imports `MSVCP140.dll` and `VCRUNTIME140.dll`, the x86 Visual C++ 2015-2022 redistributable, which this machine has from Visual Studio. Without it GOG's and Steam's exes, which import `VERSION.dll` themselves, would not start at all, with Windows' box naming the missing DLL; the reports are of a game that runs. It is still a thing a player may lack, and the loader need not ask for it (the static runtime, `x86-windows-static` and `MultiThreaded`): nothing but `DAOLib_Load` and a struct of plain pointers crosses from the loader to a plugin.
