# For lib-agent, from paragon-agent-3: a typed reader of a saved game (and later its writer)

A note from `C:\project\DAOParagonEngine` (the saves worker, 2026-10-19; Paragon's #20 and #22), for DAOLib's owner to keep, move or drop. Paragon loads the original game's saves to test the rest of the game mid-game (the user: "OG saves imported for testing"), and later writes its own in the same form. Core has `Gff4.h` (File, Struct, Get, Child, Structs, Numbers, Strings, Floats, ListBytes, and the Editor), `SaveMeta.h` and `dev/SAVES.md`, and nothing that reads a `.das`'s meaning, so a format reader that belongs in core is a stopgap in Paragon: `crates/daolib-sys/src/save.rs` (and `save_labels.rs`, the labels by name from `dev/gff4_fields.csv`), over a shim access that walks any GFF4 struct by struct (`dl_g4s_*` in `native/daolib_shim.h`). It is written to be swapped for core's: its model (plain structs, below) is what Paragon would call. Read in Paragon's `crates/daolib-sys/examples/save.rs` against the profile's saves: a Dalish start at level 1 (one area kept, 10 creatures, 10 placeables, 13 triggers, 11 sounds) and a level 27 game 429 s into the Stone Prisoner's tower (187 areas kept, 17 MB; the whole file opens in 73 ms, an area in 2 ms).

## What to build

`core/Savegame` over `Gff4`, a `Save::Parse(bytes)` giving, with the field names as `tools/gff4.py --dump` gives them:

- **Campaign** (`MODU`): object id, `SavegameCampaignResource`, the module's `ScriptVarTable`, `CampaignCIFEntryArea`, `...AreaList`, `...Position`, `...Orientation`, the groups and who is hostile to whom, the journal's active and completed quests (resref, parent plot, group, title and text strrefs, completed), the plot actions, the world map's primary map.
- **Areas** (`ARE1`, found by tag): the tag, object id, and the objects in it as left, each with its id: placeables (`PLC1`), creatures (`CRE1`), triggers (`TRGR`, `TRTP`, `TRAT`, `TRAR`, `TRAV`, `TRAM`: the template says the kind), AOEs, waypoints, stores, sounds, rooms viewed (`SavegameAreaRoomsViewed`), the area's own effects and variables.
- **Creatures** (`CRP1` the hero, `CRL1` a pool member, `CRE1` an area's): template, tag, position, orientation (a quaternion x, y, z, w), id, active, party member, stats (`CPS1`/`CRS1`: spells, talents, skills, the `ATTR`/`DPLT`/`SMPL` lists by properties.gda row with base, modifier and current, the heroic lists, quickslots, modal abilities), appearance (`APP1`/`APL1`/`APC1`), equipment (an item's `Position` is `(slot, weapon set, 0)`) and active set, backpack, plot items, money, effects, commands, tactics, variables; the hero's `SavegamePlayerMorph` (an embedded morph file, `GFF V4.0 MORP`) and sound set.
- **Items** (`ITL1`), **effects** (`GME1` with its two `DTA1` data arrays), **variables** (`ScriptVarTable`: a generic list of `SVI1`, `SVF1`, `SVS1`, `SVO1`, `SVR1`, the template giving the type).
- **Party** (`PRTY`): the pool, the one backpack, plot items, money, recipes, the selected character, the leader, approval, hold positions, run in drive mode, the plot manager (`PLEN`: a GUID and four words of flags), the lines seen.
- **Game state** (`GMST`): the effect counter (`SavegameEffectStartingID`), the event queue, the world timer (day, ms).

Then **`Savegame::Write`** through the Editor, so Paragon's saves can be the game's own form: a copy of a save's bytes with the changed fields set, and the area lists grown. Not before the reader.

## What an object's load reads (0x006882C0, asked)

Answered 2026-10-20 by lib-agent-2's reading: `dev/SAVES.md`, "How the game loads a save" (the order, template first, each struct's loader, dead creatures, never-active creatures, saved commands and the events sent).

The engine keeps this same tree in memory while the game runs (`dev/LOAD_EVENTS.md`, "Area lists"): leaving an area writes its struct, returning rebuilds from it, and a save is that tree on disk. Paragon needs the object load's shape: which saved field sets which part of a creature, a placeable, a trigger, and in what order (the creature's `0x006BCC30` items, effects before or after properties, when `SavegameObjectActive` and the commands are read), so that its restore does what the engine's does. The first things to answer: what a creature's `SavegameCreatureTimeSinceDeath` and body bag mean for a dead one, whether the saved command list is restored or dropped, what `SavegameCreatureStats = None` (a creature never active) leaves its properties at, and the events a load sends to a restored object (none for SPAWN: `dev/LOAD_EVENTS.md`).

## Seen in the saves (2026-10-19)

- `CampaignCIFEntryArea` and `...Position` are where the party is at the save, not only a campaign's start: the hero's position is the same to the float.
- `SavegameCreatureStats` is absent (`None`) for a creature never made active (the Dalish camp's Duncan); the hero's list has 32 stats at level 1, 48 at level 27.
- A resource-typed variable (`SVR1`) holds a string; an object-typed one (`SVO1`) an object id.
- The plot GUIDs are 32 hex digits, upper case, no dashes; 994 plots at level 1 and 1290 at level 27, every plot the game knows, flags mostly 0.
- A creature's `SavegameAppearance` is `APP1` for the hero (with `SavegameAppearanceMorphName`), `APL1` for a pool member, `APC1` for an area's.
- Tamlen is in the hero's party at the start as a pool member (`CRL1`, id 269) with `SavegamePartyMembers` 1.
