# What to reverse engineer next

Dragon Age's gameplay rules are mostly scripts and data. An attack's result is worked out in script (`rules_core.nss` handles `EVENT_TYPE_COMMAND_PENDING` through `Combat_HandleCommandAttack`, and `combat_h.nss` and `combat_damage_h.nss` hold the hit and damage formulas), and costs, ranges and damage values are rows of the data tables. Both are open to modders already: the toolset compiles scripts, and the override folder takes scripts and tables. Rebalancing and new formulas are done there, and DAOLib need not reach for them.

DAOLib earns its place where those cannot reach:

- **Engine state scripts cannot read or write.** No script command gives an effect's duration, for one.
- **Engine behaviour scripts cannot change.** The camera, input, time, the UI, movement and the command queue are examples.
- **Where script overrides do not compose.** A mod that changes `combat_h.nss` must recompile the 28 scripts that include it and ship them all, and two such mods cannot both be installed. A native plugin can change what those scripts do at the boundary instead (their script commands, their events), and several plugins can do it at once.

Each item says why it needs native work, what is known, and when it is done. Most valuable first. A finished item moves to `dev/LIBRARY.md`'s table, and gets an example in `examples/` when it is something a plugin would use (`dev/PLUGINS.md` says how).

## 1. Effects: duration and time left

**Read, not yet seen in play (2026-09-30):** `CGameEffect::Duration`, `Remaining`, `SetRemaining`, and the clock every temporary effect ages on, `dao/Effects.h` (`Hold`, `Advance`, `OnAgeing`), through one engine function, `AddElapsed`. Regeneration read too, and held and advanced with the effects by `dao/Clock.h`. Left: seeing both in play; giving `OnAgeing` the object the effect is on (AgeEffect, `0x007A0B10`, has it as its first argument, and AddElapsed does not); an example.

- **Why native:** scripts read an effect's type, flags, creator, ability and duration type, but no command gives its duration or how long it has left. Buff and debuff displays, and the turn-based mod's conversion of durations to rounds, need both. Cooldowns are not on this list: `GetRemainingCooldown` and `SetCooldown` are script commands, callable through `dao::script::api`.
- **Leads:** `CGameEffect` (`dao/Structures.h`, fields from the effect getter commands); `Engine_ApplyEffectOnObject`'s handler, which takes the duration; the object's effect list (`SEffectsHolder`); whatever expires effects each frame.
- **Done when:** `CGameEffect::Duration()` and `Remaining()` read in play agree with what the effect was applied with, and fall as the game runs.

## 2. Combat, at the scripts' boundary

**Done in code, not yet seen in play (2026-09-30):** `CommandCall::SetInt`, `SetFloat` and `SetObject` change a command's arguments before it runs, and `examples/damage` halves the party's damage by intercepting `SetCreatureProperty`, which `effect_damage_h.nss` calls as the one place health drops. Left: seeing it in play; a killing blow, which the scripts turn into a death effect instead.

- **Why native:** composable changes to combat without replacing `combat_h.nss`. The scripts apply damage and effects through script commands (`Engine_ApplyEffectOnObject`, `ApplyEffectOnObject`), which `dao::script::InterceptCommand` can already see and change. What is missing is reading and changing the effect in flight (its type, its floats: a damage effect's amount) and a worked example.
- **Leads:** the effect getters and setters (`GetEffectFloat`, `SetEffectEngineFloat`); `dao/ScriptHooks.h`'s `CommandCall::Structure`; `effects_h.nss` and `combat_damage_h.nss` for which floats mean what.
- **Done when:** `examples/damage` changes the damage the party takes in play, and composes with another plugin doing the same.

## 3. Input and key bindings

- **Why native:** scripts cannot read keys. A plugin polls `GetAsyncKeyState` today (the turn-based mod does), which ignores the game's own bindings and the controls screen.
- **Leads:** `GameModeController`'s `RawInputMessage` handler (`0x0063FE70`); `KeyBindings.ini`, whose bindings name messages ("SaveGameMessage -1 2"), sent through the engine's registry of message factories (`0x0078D1A0`); the data tree's `InputMappings`.
- **Done when:** a plugin registers an action, the player binds it in the controls screen, and a callback runs on the key.
- **Read so far (2026-09-30):**
  - How a key reaches the game. `KeyBindings.ini` gives each action its two keys (`TogglePause_0=Keyboard::Button_Space`). `Eclipse::GroupedInputMappings` turns a key into its action, and the action, in the current game mode, names a message as text: `SaveGameMessage -1 2`, `UserTogglePauseMessage`, `SelectPartyMemberIndexMessage 0 1`. The texts and their modes (by class name, `GameModeExplore`, `GameModeFixed`) are registered at start-up by one large function (`0x006DC900`, through `0x00891010`, `0x00890C60` and `0x0088F810`), and the message is built by name through the registry's factories and delivered.
  - What a plugin can do now. It can react to any action the player has bound by watching the message the action sends (`dao::messages::OnMessage`); the pause key's `UserTogglePauseMessage` was seen in play.
  - `RawInputMessage` is no key feed. It carries a raw input's code at `+4`, and is sent while the controls screen is capturing a key to bind (its handler, `0x00894ED0`, compares the code with Escape, Enter and the mouse buttons). It was never seen in play otherwise.
  - The actions' names in the controls screen are `inputmap.gda`, 188 rows of an id and a string reference.
  - A pressed key, end to end (2026-10-01). `keymap.gda` has each action's two default keys per language (`TogglePause_0`, `Keyboard::Button_Space`), which `KeyBindings.ini` overrides. The input's dispatcher (`0x0087D690`) finds the bindings an input matches, has each one's text made into a message (`0x0087C950`, through `0x007957D0`, which reads the text with a `Messages::InputStringDataStream`: the first word names the class in the bindings' registry of message makers, and the message reads its own fields from the rest) and sends them all to the game mode controller. `dao::messages::SendBinding` does the same from a plugin, and `SendText` the same for a movie's callback (`Receiver.Message args`), which is how `dao::gui::PressPopupButton` presses a message box's button.
  - A plugin's own action (2026-10-01). The game mode controller's start (`0x00641870`) fills the modes' groups of texts (`0x006DC900`), registers the 53 actions with their labels and what their keys send (`0x006E30D0`: `AddAction` `0x00894530`, `AddMapping` `0x00894BB0`), sets the default keys (`0x006EA9F0`: the code's own through `SetKey` `0x00894CC0`, then `keymap.gda`'s) and reads `KeyBindings.ini` (`0x006EA8F0`). An input is one word: a DirectInput scan code, the modifiers (0x100000 Shift, 0x200000 Control, 0x400000 Alt) and the device (0x10000000 the keyboard, 0x20000000 the mouse). A mode's group allows a text or bars it, and the mapper asks before it makes a message (`0x0088F430`). `dao::input::RegisterAction` (`dao/Input.h`) adds an action after the game's own, bound to a text no message has, allowed in the modes the plugin names, and takes it where the mapper asks; `examples/input/` registers two.
  - In play, 2026-10-01 (`examples/input/`): the engine took the actions, the default key ran the callback once a press and was silent under the map, the main menu and the inventory, and the game wrote the actions into `KeyBindings.ini` (`DAOLibExamplePing_0=Keyboard::Button_F11`). The controls screen did not list them. `inputmap.gda` is not the list: its 188 rows are the keys' own names ("Web Back", "ThumbLX").
  - The controls screen (2026-10-01). Its list is in its movie's script (`optionsmenu.gfx`): `AddHeader` for a section, `AddKeyBinding("TogglePause")` for each action. The library now adds a header "Mods" and a call for each plugin's action by patching the movie as the game opens it (`dao::gui::OnMovieLoad`, `dev/GUI.md`).
  - Done, 2026-10-01: in play the rows showed under "Mods", a key bound there ran the plugin's callback, and it was still bound after a restart. A plugin registers an action, the player binds it in the controls screen, and a callback runs on the key.
- **Left:** a held key (a callback on the release too) and the mouse's codes, when a plugin wants them.

## 4. Time: game speed and the clock

- **Why native:** scripts cannot change how fast the game runs. The turn-based mod wants fast AI turns, and other plugins want slow motion.
- **Leads:** the update's frame time (`Eclipse::UpdateTask`, `EclipseGame::Update`, `dao/Frame.h`); `GetLowResTimer`. The Flash UI's `SetTimeScale` scales only the menus' animations (read 2026-09-30, `dev/GUI.md`), and `GetCreatureSpeed` and `SetCreatureSpeed` are empty in this build.
- **Done when:** `dao::SetTimeScale(0.5)` slows animation, movement and effect timers together in play.
- **Done, seen in play (2026-09-30, 20:02):** at speed 2 a creature's own time ran about 2020 ms a wall second and the hero 8 to 9 m/s against 4.5. What made it work, found by a meter: a meter in `examples/speed` showed a creature's own time at 1000 ms a wall second "at speed 2". The application's frame update rewrites the world timer's scale each frame from the game's own time scale (`CClientExoApp+0x2C8`, set by `SetTimeScale`, `0x005D81C0`, what the game's slow motion uses), and gives the scale to the scene too. `SetSpeed` now calls `SetTimeScale`.
- **Before that:** timed runs found movement (4.5 m/s), walks and swings unchanged at speed 2, with the scene's frame timer scaled and, in a trial build, the renderer's (`+0xB8`) as well; the world clock does double; the user, watching, saw moves and swings faster. Next: find the time a creature's movement and animation advance by (its `MovementController`, the animation's update) and whether either reads a clock of its own.
- **Done, seen in play (2026-09-30), but see above:** `dao::clock::SetSpeed(scale)` scales both of the game's clocks: the world timer its rules run on (`EC::WorldTimer`, the application's `+0xD4`, whose update multiplies each frame's seconds by a float at `+0x54` the engine never changes), and the frame timer its animation runs on (an `EC::ITimer` at the Eclipse game object's `+0xB4`, through a hook on `EC::ITimer::Update`). The world timer alone changed nothing visible; with both, `examples/speed` at 2 made a fight visibly twice as fast, sound in step. A player-facing mod to speed up or slow down combat would build on it (proper rebindable keys wait on item 3).
- **Read before that (2026-09-30):** three clocks.
  - Scaleform's `GTimer`, the Flash UI's time: its initialiser (`0x00444C00`) puts the clock function in a global (`0x00C1DAA8`), the performance counter's in milliseconds (`0x004449C0`) or `GetTickCount`'s (`0x0041E870`), and the UI reads it through a jump (`0x004449F0`) from 31 places in Scaleform's code. Swapping that pointer would change the UI's time alone.
  - The engine's microsecond clock: the performance counter times a million over its frequency (`0x004BFF40`), on a global timer (`0x00C2BDF8`), read through `0x004BFFF0` from 31 places, among them world code (`0x0064AE30`, `0x0064B010`), the camera (`0x007E4AF0`) and more. The likeliest source of the world's frame time.
  - `timeGetTime` times a thousand (`0x0041A9D0`), 12 callers.
  - The update itself (`Eclipse::UpdateTask`'s slot 3, then `EclipseGame::Update`, `dao/Frame.h`) passes no time: the world's objects take it from a clock.
- **Next:** find where the world turns the microsecond clock into a frame's elapsed time (the AI master's and the objects' updates, which hand effects and regeneration their milliseconds: `dao/Clock.h`), and scale it there; or, as a probe experiment, scale the microsecond clock and see what slows. Scaling a clock blindly would slow timeouts and fades with it.

## 5. World queries

- **Why native:** line of sight, path length and what lies between two points are engine questions. Scripts have a little of this, but not the pathfinder's path or a raycast.
- **Leads:** `World::Raycast` (`0x006497A0`, arguments read, `dao/Addresses.h`); the pick's hits (`dao/GameModes.h`, `PickHit`); explore mode's walkable test (`0x0070C840`) and the area's check (`0x0073DE70`).
- **Done when:** `dao::world::Raycast(from, to)` and a path length agree with what the game does in play.
- **Done in code, not yet seen in play (2026-09-30):** `dao/World.h`: `Raycast` (the engine's `World::Raycast`, every shape along a ray), `FirstHit`, `LineOfSight` (the area's own test, `0x0067C3F0`, which the scripts' `CheckLineOfSight*` commands use, so doors block and chests do not), `CurrentArea`; `CCObject::Position`, `AreaId`, `Area`; `CClientExoApp::GetModule`, `CCModule::CurrentArea`. The areas' physics is PhysX; a query's mask is PhysX's groups mask, and which bit is which kind of object is read only in part (`dao::world::groups`). `examples/world` logs what it finds. Left: seeing it in play, naming the rest of the groups from its log, and a path length.
- **The pathfinder, read so far (2026-09-30):** the engine's `Pathfinding` namespace has a search environment per level of a hierarchy (`MapSearchEnvironment`, `MapAbstractionSearchEnvironment`, `MapSuperAbstractionSearchEnvironment`, vtables at `0x00B592E0`, `0x00B592F4`, `0x00B592CC`), so an A* over abstractions of the walkmesh. A search is a request advanced a step at a time (`0x00A4E1B0`: its state at the request's start, an iteration count at `+0x24`, the waypoints gathered through `0x00A48380`), not one call that returns a path. `0x00A46760` asks whether a straight line between two points is walkable (`0x00A4BB80`), and `0x00A62C90` uses it to cut corners from a creature's path (its waypoints, 12 bytes each, a vector at the path object's `+0x74`). The move-to-object command's handler is `0x007AA560`, reached through a table of handlers by command type; it picks the destination (`0x007A6CA0`) and the creature's movement asks for the path. Next: find where a request is made and stepped to its end, to give `dao::world::Path(from, to)` either by running the steps to completion on the game's thread or by reading the path a creature is given.
- **Seen in play, 2026-09-30 (the second play test):** `CurrentPath` read a walked path right (5 waypoints, 10.33 m, what was left falling as the creature walked). A `FindPath` that called `RequestPath` until it answered was taken out: `RequestPath` takes new ends only when no search is in progress (`0x0073D6E0`), so its answers came a call late, a search it left unfinished held one answer through a whole fight, and the search it left stood as the creature's path, after which the creature would not walk a click. A path on demand needs a search object of the plugin's own (the `Pathfinding` environments over the area's mesh) or the creature's search saved and put back.
- **A search of the library's own (2026-09-30), not yet seen in play:** the movement controller is a plain record (the pathfinding world, the mover's parameters, its path, the two ends), and the script command `IsLocationSafe` makes one on its stack, so `dao::world::FindPath(creature, to, toward)` makes its own with the creature's size and follows `RequestPath`'s order: the destination made a free place, the ends set, the mover's own obstacle lifted, a straight walk tried, then the search in slices until it answers. The creature's own search is not touched. `examples/world` logs a walk to whatever is under the cursor. Seen in play 2026-10-01, after a second version that moves the search's walker along and counts a path only if it arrives (`dao/World.h`). The search's answers as read and seen: 4 a coarse route found, 3 a stretch worked out, 7 both ends in one sector, 6 a door in the way, 1 done. Left: 2.

## 6. Dialogue

- **Why native:** scripts run inside a conversation's callbacks, and conversations are authored in the toolset. Changing a conversation at run time (a line, a choice, a condition) is out of their reach.
- **Leads:** `GameModeDialog`; the dialogue's messages (`SelectResponseMessage`); the conversation resource, a GFF file (`tools/gff4.py` reads the format).
- **Done when:** a plugin sees each line and choice as it is shown, and can add or hide a choice.
- **Done in code, not yet seen in play (2026-09-30):** `dao/Dialogue.h`. The engine's conversation object holds its file (GFF4 `CONV`), and a line is offered only if `Conversation::IsLineAvailable` (`0x007F0D30`) passes it, so `OnLineAvailable` can hide any line or offer one whose condition fails. `OnNpcLine` (on `PlayLine`, `0x007F1EF0`) and `OnReplies` (after dialogue mode's `ShowResponses`, `0x00690B70`) see what is spoken and offered. The lines are read from the file by a GFF4 reader in `core/` (`Gff4.h`, `Conversation.h`), tested, and checked against `tools/gff4.py` on 104 of the game's conversations. `examples/dialogue` logs a conversation. Left: seeing it in play; choosing a reply from a plugin (`SelectResponseMessage`); adding a line the file does not have, which would mean giving the engine a changed file.

## 7. The engine's messages, typed

- **Why native:** every message class a plugin can read is a hook point (`dao/Messages.h`). 11 of the 296 have fields in C++.
- **Leads:** `dev/messages.csv`, with each class's size from its clone (`tools/messages.py`); each handler's reads.
- **Done when:** the messages for abilities, the party, inventory and dialogue are typed, and each field has been seen in play.

## 8. A plugin's own strings

- **Why native:** a plugin's text today is English in code. A talk table of its own, beside the game's, would give it the player's language.
- **Leads:** `CTlkTable` (`dao/Tlk.h`, `0x004E4990`); `tools/tlk.py` reads the format; how the game loads an add-on's talk table.
- **Done when:** `dao::tlk::String` finds a plugin's string by its id, in the player's language.
- **Done another way (2026-09-30):** `dao/Strings.h` loads a plugin's own talk tables from beside its DLL (`<name>_<locale>.tlk`, falling back to en-us), by the game's language (`[GameOptions] Locale` in `DragonAge.ini`), through a talk table reader in `core/` (`TalkTable.h`, tested, and the same 51,846 strings as `tools/tlk.py` from `core_en-us.tlk`). The engine's own tables are not touched, so a plugin's ids need not avoid the game's. Left: the female forms (`_f.tlk`), and adding to the engine's tables, if a plugin's text must reach the game's own UI by strref.

- **Inventory and items.** Much is scriptable already (`GetItemsInInventory`, `CreateItemOnObject`). Native work waits for a need scripts cannot meet.
- **Party and follower AI.** Members, tactics presets.
- **Saves.** Why one quicksave in play wrote its files without `SaveGame::Write` (`dev/SAVES.md`).
