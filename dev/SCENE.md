# The renderer's scene: its objects and each one's tree of nodes

Read 2026-10-22 by lib-agent with subagents, for DAOLib #244 (the library's `dao::scene`, a plugin's view of the whole scene as a tree, as Blender's outliner shows one) and #242 (the room models' emitters). The first reading of the rooms' models (#242) had three things wrong that this one corrects: the scene, an Object's root node and its scale; they are given here as read.

[C] read in the disassembly or data, [I] inferred, [X] not read. Builds on the #242 reading, src/dao/GraphicsNodes.h, World.cpp (ModelBoxOf), Vfx.cpp, Objects.h (CCArea::Scene), dev/EFFECTS.md (:649, :670, :1133), dev/CHARACTERS.md:99, dev/CAMERA.md. Helper scripts: lib-agent-calls.py (call/jmp rel32 scan), lib-agent-vcalls.py.

## 1. The graphics scene

- **Class `Graphics::ISceneInstance`**, vtable 0x00AF7838 (3 slots), object size 0x100 [C: allocated 0x100 by 0x0053A4C0, constructor 0x00539FE0 stores the vtable at 0x0053A013; destructor 0x00539920]. Slot 0 0x0053A340 = object added (tells the cutoff +0xD4 and the managers +0xD8/+0xDC/+0xE0), slot 1 0x00539710 = object removed, slot 2 0x0053A3D0 dispatches event 2 to AddObject, 1 to RemoveObject (EFFECTS.md:649).
- **It is one object that is both the graphics scene and the holder of the physics scene**: +0x90 the Object list, +0xB0 a second vector of Objects, +0xC8 / +0xCC the physics manager and the `Physics::PhysicsScene` (0x00537D60 = `mov eax,[ecx+0xCC]`; the add 0x0053A260 calls [+0xCC] slot 0x94 and a physics slot 0x10 for an Object whose flag 0x40 is set), +0xD0 a "deferring" byte, +0xD4 the cutoff (0x00467750), +0xD8, +0xDC (`Renderer::LightManagerDefault`), +0xE0 managers, +0xE4 a deferred queue. COLLISION.md's "area +0x62C is the physics world" is the same pointer seen from its +0xCC: no contradiction, and no second scene object. [C]
- **Area +0x62C is this scene** [C]: the CCArea constructor 0x006892A7 calls 0x0040AE60 (the module's scene factory, which asks `g_graphics` 0x00C31650 slot 0x34 for a scene) and stores it at `[esi+0x62C]` (0x006892AE). Objects.h `CCArea::Scene()` is that read; `World::CurrentScene` 0x00648B30 reads it too.
- **Layout +0x4E0 is the same pointer** [C]: the layout (`EC::ChunkManager`, area +0x658) is given the scene by 0x005C9690 (`mov [esi+0x4E0], [ebp+8]` at 0x005C96D0), called only at 0x0068B45C in the area with `push [ebx+0x62C]` (`mov esi,[ebx+0x658]` at 0x0068B445). So the #242 reading's [I] is now [C].
- **Path for a plugin**: `dao::world::CurrentArea()` -> `area->Scene()` (area +0x62C) -> list at scene +0x90. Check `*(void**)scene == Module::Address(ISceneInstance::vftable)` (0x00AF7838) before use. Not a path: CClientExoApp::Get() and the layout need nothing more.
- **Other scenes exist** [C by Objects.h notes, play 2026-10-11]: a portrait and the inventory's figure are each drawn as a scene of their own, made the same way (0x0040AFE7 is the second caller of 0x0040AE60); the cutscene/chargen stage is a real area with its own +0x62C. `CurrentArea()->Scene()` is the world's. An Object knows its own scene (below), so `Object +0x25C` gives any Object's scene. A list of all scenes was not looked for [X].

## 2. The list at scene +0x90

- **MSVC 2005 `std::list<Object*>`, checked-iterator build** [C]. Constructor 0x004C5C60 (scene+0x90): `+0` proxy (unused here), `+4` head (sentinel) node (made by 0x006499B0: `next = prev = itself`), `+8` size, `+0xC` the null value that "end" derefs to. So scene `+0x94` head, `+0x98` size, `+0x9C` null. Node (12 bytes, 0x00538A00): `+0` next, `+4` prev, `+8` value. begin = `head->next`; end = head. Walk with `for (n = head->next; n != head; n = n->next) obj = n->value`. 0x004DF670 (begin: size 0 gives &list+0xC, else `head->next` + 8) and 0x0071C190 (increment: `node = node->next`, ends when node == head) are the engine's own and read exactly this.
- **The value is the Object base** (the class pointer, `Graphics::IAnimatable` at +0), not the +8 interface. 0x0053A260 (AddObject, `this` scene, arg = the +8 interface) does `add edi,-8` and pushes `edi` through 0x0054B3E0 (push_back: node 0x00538A00(next=head, prev=head->prev, value)). The cutoff walk 0x004670C0 takes each value E, calls `(E+4)->slot 1` (Object's IRenderable slot 1, 0x0054F890 = `lea eax,[ecx+0x5C]`, so Object +0x60) and reads that vector's begin/end at +4/+8 = **Object +0x64/+0x68**, the node-interface vector of the #242 reading [C].
- **Other things AddObject does** [C]: slot 0 of the scene; Object primary slot 42 (0xA8, 0x0054F620) stores the scene in **Object +0x25C** (slot 41, 0x0054F610, reads it); if the physics scene exists and the Object's flags (+8 interface slot 0xA4 = `return [Object+0x260]`... i.e. iface +0x258) have 0x40, a physics add; and unless flag 0x40 is set, the Object is also pushed on the vector at scene +0xB0 (the drawn list [I]).
- **Remove**: `Graphics::ISceneInstance::RemoveObject` **0x005395B0** (`this` scene, arg = +8 interface, 24 direct callers): checks membership with 0x00538ED0, removes from +0xB0 if it was put there (0x004E9640), erases from the list with 0x00745230, calls scene slot 1, and takes it out of the physics scene. Object primary slot 42 / its destructor (0x0054F34E, `FUN_005395b0(this+8, 0)` on +0x25C) also call it. [C]

## 3. An Object

- **One class: `GraphicsStructures::Object`**, 0x310 bytes (allocated by 0x00568590, `push 0x310`), 5 vtables [C]: `+0` primary 0x00AF85DC (64 slots; `Graphics::IAnimatable`), `+4` `Graphics::IRenderable` 0x00AF85B4 (9 slots), `+8` `Graphics::IBaseObject`/`IMemoryFootprint` 0x00AF8434 (95 slots), `+0xC` `Physics::ISimulatable` 0x00AF83FC, `+0x10` `FacialAnimation::IFaceAnimatable` 0x00AF83E4. The primary vtable is stored only in the constructor-side code (0x0054F260) and the destructor (0x0054F9EE): no subclass in the exe. Creatures, placeables, items' parts, effects, room props and portrait rigs are all this class; what differs is the blueprint (nodes) and who holds it. `--vtables Object` shows no derived class. [C]
- **Fields** (Object base offset): model name = `[+0x40]` blueprint, its `+0x8` a std::wstring (GraphicsNodes.h) [C in play]; node-interface vector `+0x64/+0x68`; light vector `+0x74/+0x78`; place `+0x100` Vector4 (IRenderable slot 3 0x0054F6F0 reads iface+0xFC = Object +0x100; written by `+8` slot 6 0x00547940 / slot 4 0x00543470); orientation quaternion `+0x120` (IRenderable slot 4 0x0054F720 reads iface+0x11C; the #242 reading's "+0x11C" was the interface offset); **uniform scale is a float at Object +0x5C** (SetScale 0x00545330 stores `[iface+0x54]`; World.cpp `kScale 0x58` from the renderable; the #242 reading's "+0x11C scale" was wrong); flags +0x260 (bit 1 shown, 0x20 emit, 0x40 no draw list, 8 cutoff override); scene +0x25C; sub-object +0x250; animation task +0x2A4 (primary slot 2); remote-material decal +0x2F8/+0x2FC; **+0x58 a node of the tree (below)**; +0x1BC an owned object that receives the place (physics/animation side, not a node) [C for the reads].
- **Place semantics**: written with the world place (0x0053A510 composes the record's with the room's). Object +0x100 with +0x120 and +0x5C is the model's world transform [I, as the #242 reading].
- **Owner in the game: game object -> Object, one way** [C]:
  - `CCObject +0x154` = the animation set / model holder (creature: World.cpp `ModelBoxOf`; effect: Vfx.cpp `ModelObject`; 0x007E36B0 / 0x007E3D30, called from `CCObject` code at 0x0068DF79 and 0x00692C7E, add "the object's model (+0x154)" to the scene, EFFECTS.md:670). `[+0x154] +0x18` -> `[ +4 ]` = the Object's **+8 interface**; Object base = that - 8. The creature path also reaches it by that holder's slot 19. Placeables and items go through the same CCObject field [I: same code, not each type read]. Weapon, armour and gore parts of a creature are further Objects held by `AnimBase*` (+0x1E0 of the CCObject, 0x00A5C7F0, 0x00A66B2A) and attached to a node of the creature's Object (0x0054D860; the attach list is at Object +0xA4/+0xA8, entries 0x4A0+ bytes, [I] attach dependencies).
  - **No back pointer was found**: Object has no ObjectId. Searched: the Object's fields above; the +8 slots 93/94 (0x0054F670/0x0054F690) are the remote-material pair (EFFECTS.md:338), not user data; nothing calls a user-data slot (scan for `call [reg+0x174/0x178]` found none). The animation events are keyed by the creature's id inside Animation::, not on the Object [X]. To name an Object's game object, build the reverse map once per frame by walking the area's objects (`CCObject +0x154` chain) and keying on the Object pointer. Items on a creature need the equipment's items, not read [X].
  - **Room model -> room** [C]: the room's `std::vector` at `CRoom +0x2A8` holds the +8 interfaces (the #242 reading 1). No field on the Object names its room [X]. An Object that is in no room's vector and not a CCObject's is a stray (effect, weapon part, portrait rig, bounding sub-object).
  - **Effects**: `CCVisualEffect +0x154` as above; its emitters are nodes of that Object.

## 4. The node tree

- **Node = `GraphicsStructures::ObjectNode`** (primary vtable 0x00AF9764 for the base, 33 slots; `+4` 0x00AF9740, `+8` 0x00AF972C, `+0xC` 0x00AF9720). Constructor 0x0055ED20(this, owner Object, blueprint) [C]. Fields: `+0x10` child vector (MSVC8 vector rep: `+0x14` begin, `+0x18` end; elements are full **node pointers**, 4 bytes; 0x00571878 .. all callers use 0x0055F060), **`+0x170` parent node** (set by AddChild 0x0055F060: `vector.push_back(child)` through 0x0049D170, then `child->+0x170 = this`; 0 for a root) [C], `+0x154` owner Object base, `+0x174` blueprint (`+0xC0` name wstring; `+0x108` a flag the Object reads from the top node, 0x00543E70), `+0x15C` an interface of the node it is attached to (not the parent), `+0x168` index (-1), `+0x179` a byte. The tree is built by the blueprint's Instantiate (blueprint slot 2, e.g. `ObjectNodePointLightBlueprint::Instantiate` 0x0055FAC0): it makes the node in a contiguous arena (`+0x1C0` bytes per light node), copies the rest transform and calls AddChild for each child blueprint (blueprint `+0xFC/+0x100` vector). The recursion over a built tree is node slot 25 (0x0055E860: blueprint slot 6 on the node, then slot 25 on each child) [C].
- **Root**: **Object `+0x58` is a node of the tree** [C: its `+0x170` is climbed to the top in 0x00543E70 (Object primary slot 58), the Object's destructor 0x0054F41A deletes it through its slot 0, 0x0054273F-0x00542766 call its slots 22/23]. The top after climbing `+0x170` is the root; whether +0x58 is itself the root is [I] (it usually is; climb anyway). A walk: `root = node = Object+0x58; while (node->+0x170) node = node->+0x170; recurse over +0x14..+0x18`. The root's `[+0x174]+0x108` flag is read by the Object. (the #242 reading's "Object +0x1BC root" was wrong: +0x1BC is an object that gets SetPosition, not a node.)
- **The flat vector Object +0x64/+0x68** holds only nodes that have the 35-slot `IRenderableNode` interface at **node+0x180** (kind below); lights are in +0x70/+0x74 (6-slot `ILight`). Bone, Crust, SnaptoPoint, UsePoint, EmitterTarget and the plain `ObjectNode` have no interface and appear only in the tree. [C]

## 5. Lifetime and threads

- **Enter** [C]: 0x0053A260 callers: level load 0x0053A510 (from 0x005CEA80 `.rml`, 0x005CC770, 0x005D2970 = room slot 24 take-in), a creature/object's model 0x007E36B0 (per-object state machine 0x007E3D30), `AnimBase` slot 1 and 0x00A5C7F0 (weapons, gore), a model swap 0x0054E180/0x0054E23B, effect models (0x0079D410 -> model interface), portrait/chargen 0x007BB890, 0x007F410A, 0x005C88E0, 0x00602B70 (EFFECTS.md:670). **Leave**: 0x005395B0 by room unload (slot 8 0x005D30E0 deletes each Object, whose destructor removes itself), by CCObject slot 66 (hide by distance, the model comes out of the scene), by a model swap, and when a creature or effect is destroyed. An Object can be out of the scene and alive (hidden creature) or in it without a room.
- **Thread** [I]: nothing in AddObject/RemoveObject takes a lock (0x0053A260, 0x005395B0 read in full above); Objects are built in worker tasks (ConstructObjectTask 0x00572C40 calls the manager slot 4 0x0057B370) but placed in the scene at the take-in / by the object state machine on the game thread (the same reading as the #242 reading 4, direct callers on the game thread not each checked). The readers of the list are the cutoff (0x00467102, from the camera update on the frame thread), 0x00539D4A and 0x007D4351. So reading from the frame callback is as safe as the cutoff's own walk; use `TryRead` for every pointer, snapshot the pointers in one pass, do not keep them across frames. Animation and emitter tasks run on task threads (ANIMATION, EFFECTS) and write matrices and particle state; a node's matrices read from the frame thread may be one step old. [I]
- **Not read** [X]: a list of all scenes; Object -> game object back link; room of a non-room Object; what `+0xA0` matrix is; whether Object +0x58 is always the root.

## 6. dao::scene and its cache (DAOLib #244)

- **What is kept** (`src/dao/Scene.cpp`, 2026-10-23): the object list in the scene's order, each Object's tree as its nodes' addresses and classes (preorder) with a bit per kind present, and the rooms' models' room numbers. Read at each call: an Object's place, scale and model name, each node's world matrix and name, and the owners (game object -> Object, through `+0x154` -> `+0x18` -> `+4` - 8, from the area's objects and the running effects), since a game object can take its Object after the Object joined the scene.
- **When it is read again**: the three are detoured on first use, `AddObject` (7474, after the call) and `RemoveObject` (7458, before it) mark the list changed and the Object's tree to be read; `AddChild` (8352, `ret 4`, pushes onto `this+0x10` and sets the child's `+0x170`) marks its node's Object (`node+0x154`) if the cache holds it. A changed scene pointer (another area) drops everything. [S] in release, 2026-10-23: every root's `+0x154` is its Object (340 of 340 in Redcliffe castle, 723 of 723 in the village by night, 459 of 459 in the Deep Roads grotto), and the cache matched a fresh read of the whole scene on every 5 s check through two area changes and objects added and removed.
- **Removing a child** [I]: no code in the exe was found clearing a node's `+0x170` to zero (a scan for `mov [reg+0x170], 0` found two, both of other classes); trees seem to lose nodes only with their Object. The probe's check against a fresh read would show one that does.
- **Cost** [S], release, per call: `scene::ForEach(Kind::Emitter)` for `vfx::RunningEffects`' rooms' fires, with the rest of RunningEffects, 60 us in the castle (15 effects, 8 of them rooms' fires), 130-155 us in the village (94, 25), 77 us in the grotto (13, 5); the old RunningEffects, without the rooms' fires, 7-16 us in the castle. The full tree from the cache about 0.6 ms in the castle (2,567 nodes), 1.1 ms in the village; read fresh, about 0.8 ms in the castle. Most of what is left in a ForEach is the owner map.
