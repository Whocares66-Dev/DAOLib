# The game's files: where they are, and which copy the game uses

The game finds a file by its name with its extension (`rules_core.ncs`), in one of a few hundred places: folders, archives (`.erf`), and archives read whole (`.rim`). Many names are in more than one place: a patch replaces a core file, an add-in or a mod replaces either, the player's override folder replaces everything. This is which copy the game takes, read in the exe and seen in play (DAOLib #106, step 4, 2026-10-12). A tool that reads the game's files with no game (Eluvian's ghilana) answers by these rules, which `dao::core::install::Index` (`dao/core/Install.h`) applies: each resource's copies in the game's order, the one it takes first, each with its priority, and why the game has none of a copy (another campaign's, a level's own, another language's or texture quality's, a disabled add-in's). A plugin in the game asks the game itself: `dao::resources::Sources()` lists every place in the order the game looks, and `dao::resources::SourceOf(file)` says where a file is taken from (`dao/Resources.h`).

## The rule

The resource manager keeps its sources in one list, ordered by:

1. **priority**, lower first;
2. **kind**, a folder before a RIM before an ERF (each source's slot 8: a folder 0 or 1, a RIM 2, an ERF 3);
3. **name**, the later in the alphabet first (the source's name: an alias and a file, or a folder's path).

`AddSource` puts each new source before the first that sorts after it (0x004E6660 compares, `dao/Addresses.h`, "The resource manager's sources"). Its index keeps, for each file name, the sources that have it in the same order (0x004C7C50), and **a file comes from the first source in that order that has it**.

An archive found inside a folder source (the game's own `packages\core\data\*.erf`, an `.erf` in a plugin's `override\`) is a source of its own at the folder's priority, so a loose file beats an archive beside it, and of two archives in one folder the later name wins (`patch004.erf` before `patch000.erf`).

**A name asked of `Resources::Find`** (0x004D5BA0 → manager 0x004C5C80; read 2026-10-29 by lib-agent-2 with a subagent) [C unless marked]: the name is lower-cased in ASCII (0x004C3A50) and truncated nowhere; its last three characters are the type's key, looked up in a map at manager +0x14 (0x004C5D02) without being stripped; and each source of that type is asked for the whole lower-cased name, extension included. The type argument the callers pass (3 for a script, at 0x00AF046C) is no filter: it goes to the handle's load (0x004BECD0) [I for its meaning]. So `foo.ncs.ncs` finds the type and no source, and returns an empty handle.

**Add-ins.** The enabled add-ins of `Settings\AddIns.xml` are taken in descending order of their `Priority` attribute (in the order below), and the *i*-th (from 0) gets a base of 9000 − 7*i*: under `ADDINS:` if the add-in's folder is in Documents, else 10000 more under `BUILD_ADDINS:` (0x005ECB30 tries the one, then the other, 0x005EF460 counts down from 9000 by 7). So **an add-in with a lower `Priority` attribute wins**: here the promotional items' (`Priority="1"`) at 18734 and up, the Golems of Amgarrak's (`595`) at 19000. Within one add-in, its `core\` and, while it extends the loaded campaign, its `module\`, each folder by the alias the loader asks with (0x005EF460, the names pushed before each call): `data` and `env` at the base, `audio\sound` −1, `audio\vo\<language>` −2, `textures\<quality>` −3, `locale\<language>` −4, `patch` −5, `override` −6. Seen in play: the base, −2, −3 and −6; this install has no add-in with the others.

**The order of add-ins of equal `Priority`.** The game takes `AddIns.xml`'s items from the last to the first and sorts them by `Priority` with MSVC 2005's `std::sort`, which is not stable, so add-ins of equal `Priority` come out in an order of the sort's own, neither alphabetical nor the file's. Running that sort (`dao/core/AddInOrder.h`: its `_Sort`, `_Unguarded_partition` and `_Insertion_sort` step for step) over this install's items gives the order the game took: all 39 add-ins, the 17 in groups of equal `Priority` among them, and all 9 offers (`offers.xml`'s, the same way). `install::Index` over this install gives every add-in's priority as the game's own list had it, 39 of 39. Reproduced, not read in the code: how the list is made and sorted is not traced.

**Offers.** An offer is not a DLC but its advertisement: what the game shows of a DLC the player does not own. Each DLC is in the install twice, as an add-in (`Addins\DAO_PRC_CP_1\`, the content: its module, data, levels, voice) and as an offer (`Offers\dao_prc_ocp_1\`), whose `manifest.xml` is `<Manifest Type="Offer">` with an `OfferItem` (`o_PRC_CP1_Cailan`, `Presentation="16"`), the DLC's title and store text. An offer holds little: Return to Ostagar's a `gui.erf`, a `2da.erf`, models, animations and talk tables; Leliana's Song's a `gui.erf` and talk tables; the Blood Dragon armour's one picture (read 2026-10-12). Behind everything, an offer can only add names no other source has, and never shadows the core or the DLC it sells, which may be installed beside it as here. Where each offer shows in the game was not looked at.

**Sources that come and go.** The campaign's are added when a campaign loads and the level's `ENV:` RIMs while the level is loaded; neither is there at the main menu. A plugin's folders come with the plugin.

**Movies.** A `.bik` is found by name in the same order, among the folder sources alone: never in an ERF or RIM, and the current language's `locale\<lang>\` before `data\movies\` in each tier (`dev/CUTSCENES.md`, "A movie (.bik) as the engine plays it").

## Merged tables

A data table the game merges (an M2DA: abilities, items, portraits, most of what the scripts' `TABLE_*` name) is not one winning file but the rows of many: the core's `abi_base.gda`, an add-in's `abi_cp1.gda`, a mod's `abi_mymod.gda`. Read in the exe 2026-10-13 (`dao/core/M2da.cpp` has the addresses) and seen in play:

- **Which files.** At start the game lists every GDA file it has, its sources in the order above, each name once, from the source that wins it, and **one source's files by their names** (in lower case, character by character: `_m10` before `_m9`), whether the source is an archive or a folder. `m2da_base` is itself merged, from every file starting `m2da_`. Then each of its rows makes a table of the row's `Worksheet` from **every file whose name starts with the worksheet, in any case**: so `aip_archer_dwarf.gda` would be part of `aip_archer`'s table as well as its own. But a row whose ID is **10001 to 10999** (the AI's packages, `aip_*`) is a single table, loaded from the one file of the worksheet's own name and not merged. A file whose first column is not `ID` gives no rows.
- **Which row.** The table's rows are one array sorted by ID, filled file by file in the list's order, and **a row whose ID the table has already is dropped**: of the rows of one ID, the game keeps the first file's, which is the file of the source looked in first. An add-in's or a mod's row beats the core's of the same ID, and a mod in a plugin's or the player's override beats an add-in's. Two rows of one ID in one file: the first.
- **Seen in play** (GOG's game, the script commands through Eluvian): `GetM2DAInt(268, "TitleStrRef", 25)` is 445854, from Awakening's `achievements_ep1.gda`, where the core's `patch003.erf` has `-1` in `achievements.gda`; `GetM2DARows(10076)`, `aip_archer`, is 12, its own file's rows and not the 14 with `aip_archer_dwarf`, `_elf` and `_human`; `GetM2DARows(4)`, `prj_`, is 76, `prj_base.gda`'s 67 and more, which a rule of the longest prefix (`prj_base` is a worksheet too) would have left at none.

One source's order was seen in play, not read in the code (2026-10-13): test copies of `achievements_ep1.gda` (table 268), each giving row 25 a value of its own, in one ERF in a plugin's `override\` folder, ahead of every add-in, and the game asked for the row through Eluvian's script tool. Of `achievements_zz1` and `_zz2`, the first, whichever the archive's entries put first; of `_b` and `_a`, `_a`; of `_q` and `_c`, `_c`; of `_m9` and `_m10`, `_m10`; of five files in a shuffled order, `_b2`, the first by name; and of `_y`, `_e` and `_s` loose in the folder, written in that order, `_e`. Seven of seven the first by name, where a hash's order would have matched them all once in more than a hundred.

The world map's `.map` files are listed the same way (`WorldMap::LoadMapResources` 0x00701990 calls `ListNames` 0x004C56B0 with the type `MAP` exactly as `GdaStore::Load` does with `GDA`) and loaded in that order, unsorted, so an add-in's map, and the pins it gives its parent, come before an offer's (read 2026-10-23 by lib-agent-2, for #251). `install::Index::Listed` gives a type's files in that order.

`install::Index::SortFiles` puts a table's files in that order, and `dao::core::m2da` applies the rest: `WorksheetsOf` gives every worksheet a file is part of, `Takes` says whether one is, and `Merge` marks each ID's row the game keeps (`taken`), given the files in the game's order.

FMOD's banks and projects (`.fsb`, `.fev`) are opened through the resource manager too, by the order above: FMOD is given the game's own file system, whose open asks the resource manager for the name (read in the exe 2026-10-18, not seen in play; `dev/AUDIO.md`).

## Talk tables

The text of a string id is not one winning file but the first of a list of tables that holds the id; which tables and their order were read in the exe and seen in play 2026-10-24 (DAOLib #106; `dao/core/TalkTables.cpp` has the addresses). `install::TalkTables` gives the list, `install::Strings` the text.

- **A name's table.** The engine loads a table by a name: `<name>_<language>.tlk`, or `<name>_en-us.tlk` where the resource manager has no such file (seen: a German game took an add-in's English table), then `<name>_<language>_f.tlk` marked female, where there is one. Nothing is loaded, and nothing logged, where neither is found. The file is found by the order above, so an override's copy wins. The language is the profile's `Settings\DragonAge.ini` `Locale` (`en-us`; a German game with `de-de`), not the registry's `language`.
- **The load order.** At start: `core`, then every enabled add-in's `<UID>_c` in the order the game takes the add-ins (the higher `Priority` first, the reverse of their resources, where the lower wins), then every offer's `<UID>_c`; these are all the main menu has. As a campaign loads: its `.cif`'s packages', each add-in's and then each offer's module table `<UID>` that extends the campaign, and last the campaign's own, by its name (`singleplayer`). Leaving a campaign takes its tables away again. Seen with a test add-in whose tables each shared an id with another's: the core's before any add-in's, an add-in of `Priority` 500 before Return to Ostagar's 200 before one of 1, the offers' core tables after the add-ins' and before every module table, an add-in's module table before an offer's and before `singleplayer`'s. Leliana's Song's save had none of `singleplayer`'s, nor the module table of an add-in for the main campaign.
- **The gender reorders them.** No lookup reads a gender: `GetTlkTableString`'s gender argument changed nothing. Instead, each time the hero's gender is set (as a campaign loads, by `SetPartyLeader`, by `SetCreatureGender` on the hero), the tables of that gender (the `_f` ones, or the rest) move ahead of the others, in reverse of their order. So a female hero's German game shows core's `_f` "Magierin" for 238912 and a male hero's "Magier"; and in a male hero's game the plain tables are reversed: an add-in's table before the core's, `singleplayer`'s before an add-in's module table. Setting the hero's gender male, female, then male again reversed the plain tables, left them, and put them back. Where two tables hold one id with different texts, which is shown can change in a session; in the vanilla en-us tables no two hold an id with different text (1,596 shared ids, read 2026-10-23).
- **The file's own search.** A table's list of strings is an open hash table: an id is searched from its hash's slot, one slot on at a time, until the id, an empty slot (id `0xFFFFFFFF`) or the start again. Every shipped table is laid out so: over the GOG install's 84 tables of the main campaign, the game's search finds every one of 207,437 ids. A table with no empty slot is searched whole: seen in play 2026-10-24, a test add-in's tables written with every slot full, the ids off their hash's slot, each found. An id with no text (its string's offset `0xFFFFFFFF`) is found with an empty text, and so hides a later table's (0x00456140 gives the constant 0x00ADEF14 for that offset); no two vanilla en-us tables have an id empty in one and with text in the other.
- **The file's layout.** Every one of the install's 1,501 tables is laid out by the same rules, each rebuilt byte for byte from its ids and texts (2026-10-24): the list a third more slots than strings (the count times four thirds, rounded down), the ids put in from the lowest, each at its hash's slot or the next free one; a free slot's id and offset `0xFFFFFFFF`; the texts after the list in the slots' order, each on four bytes after bytes of `0xFF`, a text two ids share written once, an empty text not written (offset `0xFFFFFFFF`); a table of no strings, 663 of them, no list at all (the top struct's offset `0xFFFFFFFF`). `TalkTableFile::Write` writes by these rules, and `tests/test_talktable_roundtrip.cpp` (hidden) writes every table back to its own bytes.

## Archives

An archive of version 2.0 (the core's `.erf` files and every `.rim`) is laid out the same way in all 10,257 of the GOG install's (seen 2026-10-24, DAOLib #106): the header (`ERF V2.0` in UTF-16, the count, the year less 1900 and the day of the year it was built, `0xFFFFFFFF`), then the entries in their names' order, every name lower case, then the files' bytes in that order, each at the next multiple of four, the gaps zero. `erf::Write` makes exactly this, and the round trip over the install (`tests/test_erf_roundtrip.cpp`, hidden) writes each archive back from its files to its own bytes. Four of `packages\core\data` (`designerareas`, `designercutscenes`, `designertriggers`, `fonts`) end in 256 ASCII hex digits more, no MD5, SHA-1, SHA-256 or SHA-512 of the rest; what makes or reads them is unread. `PC_GAMER_TALE_modcore.erf` has no files, its header alone. The add-ins' archives of version 2.2 are enciphered and are not written.

## The readers checked twice

Core's GFF4 reader has a second, `tools/gff4.py`, written apart from it: `tools/second_reader.py` walks a file by both (core's through `dao_gff4_leaves`, `tools/second_reader`) and compares what they read, value by value (DAOLib #106, step 6). Its first run, over a sample of the GOG install (up to 300 files of each of 31 GFF4 kinds, under 1 MB each, 6,288 files), found both reading a generic field's string one hop too far: a field by reference whose element is a string names the string itself, as an ordinary string field's offset does, and every one of the install's 90 string variables (a campaign `.cif`'s, 17003) is laid out so; core read them as none and `gff4.py` as garbage, and both now read them (`dao/core/Gff4.cpp`'s `GenericElement`). Since then all 6,288, and 120 of a profile's saves, read the same by both. Core's walk is `dao/core/Gff4Walk.h`'s `gff4::Walk`, every value of a file handed to a visitor in its template's order; `dao_gff4_leaves` is one visitor of it and `dao_files json` (`tools/files`) another, which writes a file as JSON with `dev/gff4_fields.csv`'s names and is what ElgaraShaders' tools read the game's GFF4 files through, and `dao_files extract` writes an archive's entries out byte for byte, in its order (both checked 2026-10-24 against `gff4.py`'s `walk()` and `script_commands.py`'s `erf_entries`, since retired: the Python tools read archives through `dao_files` with `tools/archive.py`, and `dao_files list` lists an archive's entries, each readable or not). A save keeps a string variable in an `SVS1` of its own, typed, and none of 538 has a generic string by reference: all 538 read and written back through `dao/core/Savegame.h`, 2,665 string variables among them, are their own bytes (`tests/test_savegame.cpp`, hidden). The talk tables' and data tables' readers need no second: each of the install's files is rebuilt byte for byte from what core reads of it, which a misread value could not survive.

## Data table files

A data table is a GFF4 of type `G2DA`: version 0.2 for the 1,715 data tables of the GOG install, version 0.1 for the 1,432 conversations' tables in `designerdialogs.erf`, whose columns hold their name's text as well as its hash and no type byte (read 2026-10-24, DAOLib #106). The header and templates say where each column's field is in a row. 1,709 of the 1,715 have the plain layout: the fields of four bytes and more in column order, then the one-byte fields, the row rounded up to four. Six (`apr_base` and `bitm_base`, their patches and Awakening's) keep their editing's history: a column turned into a byte moved to the row's end, later columns in the holes it left. So a table's layout is its own, kept as read. The data is laid out the same in all: the top struct; the column list, its structs as they are (version 0.2's a hash, a type byte and three bytes of `0xFF`); version 0.1's column names' texts; then on four bytes after `0xFF` the row list, every byte of a row that no field takes `0xFF`; then the rows' texts, in row order and each row's in column order, each on four bytes after `0xFF`, a text met before pointed at and not written again, an empty text not written (offset `0xFFFFFFFF`; no table of the game's writes an empty text). A table of no rows has no row list. `GdaFile` keeps the layout it reads, `Bytes` writes a table back, and `tests/test_gdafile_roundtrip.cpp` (hidden) writes all 3,147 back to their own bytes.

**The worksheets' catalogue.** `dao/core/generated/GdaSchema.h` names every worksheet the game merges and what each column holds, for tools that follow a row's references (DAOLib #106, step 5). `dao_gda_schema` (`tools/gda_schema`, over the core, either width) scans an install into `dev/gda_schema.csv`: each of m2da_base's worksheets merged as the game merges it, each column's name from its hash (`dev/gda_column_names.txt`, xoreos' 2,205 names, each checked against its hash), its type, and its kind, with the counts behind it. A kind is said only where nearly all of a column's distinct values say it, at least ten of them: a strref where 98% of its values resolve in the talk tables and none is below 1,000 (small whole numbers, levels and races, resolve by chance); a resource where 98% name the install's files of one extension; a worksheet where a `*_Worksheet` column's values are worksheets' labels. Over the GOG install (2026-10-24): 413 worksheets, 3,349 columns (48 of no known name), 45 strrefs, 15 resources; anything unclear is plain, and `dev/gda_references.csv`, kept by hand with its evidence, names a column's kind or a row of another table where the scan cannot. `tools/gen_gda_schema.py` writes the catalogue and the typed rows of the twelve worksheets callers read by column; a worksheet is named once, by the scripts' `TABLE_*` constant where it has one (`dao::script::Table`), else by its label (`tables::Sheet`).

## Templates

A template (`.utc`, `.uti`, `.utp`, `.utt`, `.utm`, an area's `.are`, an area list's `.lst`, a character's `.bic`) is GFF V3.2, which the toolset writes. Over the GOG install's 18,673 (read 2026-10-24, DAOLib #106), a file is written from its tree mostly by one rule: the root struct numbered 0; for each struct, its fields that are no list in order, a struct field numbering its child as it is written; then those children, each written the same way; then its list fields in order, each list's entries numbered as the list is written and each written right after it. Labels go in the order first used, a field's data where its field is written, the structs' field index lists in struct order, a list's indices as written. Rebuilt from its tree by that rule, a file is its own bytes for every `LST` (271), `UTI` (3,015) and `UTT` (2,087), 5,194 of 5,201 `UTP`, 6,350 of 7,304 `UTC`, 14 of 127 `UTM`, 10 of 665 `ARE` and none of 3 `BIC`. The rest put a child after a later field of its parent, by label: a creature's `ItemList` entries after its `Equip_ItemList` (953), an area's `TriggerList`, `CreatureList`, `PlaceableList` and `StoreList` entries after its `StageList` (1,805) or `SoundList` (174), a store's `WillNotBuy` after its `WillOnlyBuy` (3); and a creature's `Appearance Data` always comes after its `Race`, the field that follows it (7,302), as the rule has it. So the toolset writes each kind by a writer of its own, not by one rule on the tree, and nothing here writes a template from nothing. A mod edits one: `gff3::Editor` patches a copy and appends what grows, so a file nothing was set in is its own bytes, and `tests/test_gff3_roundtrip.cpp` (hidden) holds that for all 18,673 and makes up to five edits in each (a number, a float, a string or resref, a localised string, a number in a list's first entry), 71,476 in all, every other field read back as it was.

**The templates' catalogue.** `dao/core/generated/Gff3Schema.h` names every field of a kind of template and what it holds, and gives each struct a typed view (DAOLib #106, step 5). `dao_gff3_schema` (`tools/gff3_schema`, over the core, either width) walks every copy the game takes of a kind's files into `dev/gff3_schema_<type>.csv`: each struct by its path (`""` the top, `Appearance Data`, `ItemList[]`), each field's label, the GFF3 type the files give it, how many files have it, and its kind with the counts behind it. A kind is said only where nearly all of at least ten distinct values say it: a resource where 98% of a ResRef's values name the install's files of one extension; a strref where a whole number's resolve in the talk tables, none below 1,000; a row where `dev/gff3_references.csv`, kept by hand with its evidence, names a worksheet and 98% of the values are its rows' IDs. Over the GOG install's 2,486 creatures (2026-10-24): 19 paths, 169 fields, 5 resources (`TemplateResRef` .utc, `DialogResRef` .dlg, `EventScript` .ncs, the two item lists' `TemplateResRef` .uti) and 8 rows, each of its values its target's (`Appearance_Type` of Appearances, `Race`, `Package`, `TreasureCategory`, the talents', spells' and skills' numbers of Abilities, `PropertyList[]`'s `Index` of Properties); `Rank`, 6 of 6 values Creature Ranks' IDs, is too few to say. Over its 1,275 items: 3 paths, 30 fields, 1 resource (`TemplateResRef` .uti) and 5 rows, each of its values its target's (`BaseItem` of Items, `Material` of Material Types, `AbilityID` of Abilities, `CraftingRecipeID` of Crafting Recipes, `Heraldry` of Heraldry); `PropertiesList[]`'s `PropertyID` is 95 of 97 values itemprps' IDs, short of nearly all, and `OnHitEffectID` neither Effects' (0 of 17) nor Visual Effects' (12 of 17), so both are plain. `tools/gen_gff3_schema.py` writes the catalogue and the views: `templates::utc::Creature::Of(file)`, `templates::uti::Item::Of(file)`, `templates::utp::Placeable::Of(file)`, `templates::utm::Store::Of(file)`, `templates::utt::Trigger::Of(file)` (773 triggers: 8 fields, `EventScript` .ncs), each field a `std::optional` accessor of the schema's type, a struct field a view, a list a vector of its entries' views. Over its 1,886 placeables (2026-10-24, DAOLib #258): 3 paths, 69 fields, 4 resources (`TemplateResRef` .utp, `EventScript` .ncs, `Conversation` .dlg, `ItemList[]`'s `TemplateResRef` .uti) and 2 rows, each of its values its target's (`Appearance` of Placeables, 456 of 456; `TreasureCategory`); `Rank`, 4 values, too few. Over its 50 stores: 6 paths, 18 fields, 1 resource (`StoreList[]/ItemList[]`'s `InventoryRes` .uti) and 1 row (`WillNotBuy[]`'s `BaseItem` of Items, 69 of 70); `WillOnlyBuy[]`'s, 2 values, too few. ## What the engine keeps of what it loads (read 2026-10-20 by lib-agent-2, DAOLib #207)

Read in GOG's exe, not run in the game. [C] checked, [I] inferred.

### Data tables: every one built at start, kept for the session

- **Eager, whole.** `GdaStore::Load` (0x004E0BF0) lists every GDA file once, merges `m2da_base` (every file starting `M2DA_`), then builds each of its rows' tables from the files whose names start with the row's worksheet: about 426 tables and 20,000 rows on the base game. `FindTable` (0x004DF580) only indexes that array; its path for an empty slot reads the row's worksheet and returns the slot still null, so a table is there from `Load` or never [C].
- **Rebuilt wholesale, never per table.** `Load` runs at start (the resources' set-up, 0x0060358C), at every change of the add-in list (0x005F4610, at 0x005F5A58), when the campaign's sources are set (0x005FCE80, at 0x005FDF23), and in a `CCModule` method (0x005FC140) that deletes the store and makes a new one (0x00A2CC25; caller 0x005FC7CB). It clears every table first (0x004DF940). No release or reload on a language change or an area load was seen [C]. The store's keeper (12 bytes at 0xC1D090) lives from the application's start (0x005DBC3F) to its teardown (0x005D72E3).
- **A held table pointer dangles across a rebuild:** the old tables are deleted. The engine's own getters find the table again on each call ([0xC1D090] → +4 → `FindTable`), so they are safe [C].
- **One merged object per table.** An M2DA keeps its G2DA parts (+0x30) and one row vector sorted by ID (+0x20/+0x24, 16 bytes a row), merged at load, the first file's row of an ID kept. A row is found by binary search by ID (0x004EC130, through 0x004EC910). A column is found by a linear scan of the first part's column list (0x004ED160) on every get. There is no hash map, and no row or cell cache [C].
- **The raw file is kept, nothing parsed into cells.** A G2DA (0x34 bytes, `Load` 0x004ED340) checks `GFF V4.0`, takes its row and column counts, and keeps a pointer and size to the file image at +0x28 for its life; every get walks those bytes again [C]. About 2.5 to 3 MB for the base game: 2da.erf's 2 MB of GDAs, plus about 320 KB of row entries [I].
- The level's own `ENV:` GDA files are a separate, unmerged list kept by name (0x004E0EA0), built at start and in the store's set-up, not on an area load in anything read [C].
- **Not read:** whether a rebuild frees the old merged `m2da_base` (`Load` overwrites +0x30 without deleting it, so it may leak); whether a G2DA's image is the resource manager's buffer or a copy; what 0x004C0B00 compares exactly; why 0x004E0EA0 runs both at start and in the set-up; the time `Load` takes in play.

### Resources and templates: no byte cache, a template never kept

- **No cache in the LRU or budget sense.** A resource's record (name, source, offset, size) lives with its source for the source's life; only its buffer comes and goes. A buffer is held only while a handle to it is: the handle is copy-counted (a 16-bit count at +0x38), and at the last release (`Resources::Release` 0x004D5860 → 0x004C5450 → 0x004BF010) `FreeWhenUnused` (0x004BEDE0) frees it at once and sets the state back to not loaded, unless the buffer is the caller's (+0x3C). The next find reads the file from the archive again [C]. No size limit, setting or memory test was found in the find, the release or the free, and no list of resources kept loaded [C for the paths read, I for the absence elsewhere].
- **A template is read again for every object made from it.** For a creature (slot 117, 0x006A27B0): a new `CExoGFF` (0xD8 bytes, constructor 0x00A388F0) takes a handle to the template's file; its loader (0x00A37AB0) checks the header and points its section views into the file's bytes, with no parse and no copy; the creature reads its fields; the `CExoGFF` is deleted (0x006A28CA), which releases the handle and frees the buffer. The next creature of the same template reads the archive again; two share the buffer only while their handles overlap [C for the creature; other template kinds assumed alike, I].
- **What the engine does keep is built structures, by name:** the GDA store above, and caches named in its RTTI: `AppearanceCache`, `VisualEffectCache`, `ProjectileCache`, `TwoDimArrayCache`, glyph caches, and the module's `Mod_CacheNSSList`. A model's file is held while it is parsed, and the graphics manager keeps the built model, not the bytes [I; their contents and eviction not read].
- **Not read:** when a source is released mid-game (a module or add-in change); `Mod_CacheNSSList` and the module's resource manager; the model and animation caches' keys and when they drop; the named caches' contents; the other template kinds' opens.

### Textures: one per name, shared, released at the last user

- **No file bytes kept.** Textures are made in D3DPOOL_MANAGED; the system-memory copy is D3D9's, not the engine's [C for the pool, I that no bytes are kept: nothing holds a data pointer, and a reload reads the file again]. A DDS is parsed by the engine itself (0x0084BFA0: the magic, a 0x7C header; then 0x0084B800 and its variants create the texture, lock each mip and copy). D3DX's in-memory loader (driver slot +0xC0, 0x00869200) is for other image types [I].
- **One texture per name, shared and counted.** `TextureManager` (vftable 0xB2B2B8) keeps a name map whose entries are weak handles: the insert (0x00845D00) stores the handle and drops one strong count (0x004FA0E0). So a texture is destroyed at once when its last strong user lets go (a material's texture parameter, an `img://` image), and the name stays in the map as an empty handle that a lookup skips. A texture an area uses that the next does not is destroyed on leaving and read again on return [C for the pieces, I for the whole]. `ReloadAll` (0x00846E50) reloads every live texture in place.
- **A recycle pool of device textures** by shape (width, height, mips, format, flags; 0x00849980 at `TextureManager` +0xA0, lookup 0x00847830, a free list per shape 0x00847BE0): a freed texture of the same shape can serve the next load [C for the structure; when one is returned to it, I].
- **No LRU and no byte budget.** A texture is halved, its top mip dropped, while it is larger than the device's maximum (0x0084B8A3–0x0084B8EB) [C]. `ForceTextureMemoryLimit` and `EnableDefaultPoolTextures` are settings the options read and write (+0x1E0, +0x1F0); what uses them is not read.
- **Texture quality** (`SetTextureQuality`, 0x00459060) sets a mip skip (0x00844F70: the top mip of every texture dropped when the option is 0, none otherwise) and reloads every live texture; the same chain picks the folder, `packages\core\textures\medium` or `high` [C for the code; which option number the menu calls Low, Medium or High is not read, and the folder strings were not spot-checked by the reader].
- **Synchronous on the caller's thread,** except an `img://…?Async=1` image (the GUI's): then `TextureManager::Load` (0x00845D80) returns an empty placeholder at once and queues a `TextureLoadTask` (0x0084A930) that fills it on a worker [C].
- **Not read:** the menu's names for the quality values; who uses the two settings above; when a texture goes back to the recycle pool; the scheduler's threads; what an area unload does to its materials; cube and volume textures.

### Against core's own (dao/core/Install.h)

- **Tables:** `Index::Table` and `Index::Worksheet` keep tables for the index's life, as the engine keeps its whole store for the session. Core builds a table when it is first asked for, not all at start; core keeps parsed cells where the engine re-walks the file's bytes on each get.
- **Bytes and templates:** like the engine, core keeps no file bytes and reads a template again each time it is asked for. A `gff3::Struct` is a list of field views into the bytes, as the engine's `CExoGFF` points its views into them.
- **Textures:** core keeps none. Keeping them is the caller's, as the engine keeps its GPU textures by name while they are used.
